## TK-208 보완 — 미완독 쪽이 영구히 남는다

### 문제 (운영 2회차, 배포 aaf51806)

7개 부분 읽기 자료의 실행 미완료 16쪽(예산 11·OCR 저품질 5)이 **두 동기화와 서면9 세 실행에 그대로**
남았다. 2차 동기화에서 41개 중 40개가 재사용됐고 내려받기는 1건뿐이었다. 쪽 단위 이어 읽기가
전혀 관찰되지 않았다.

### 원인 — 평가 측이 재현으로 확정했다 (SHA `37a74def` 기준)

두 결함이 겹친다.

**D1. 예산과 무관한 실패를 `BUDGET_EXHAUSTED`로 적는다.**

- `packages/rag_engine/extract.py:190-194` — `pypdfium2.PdfDocument(path)`가 실패하면 `native = None`으로
  두고 pypdf로 계속한다.
- `extract.py:266` — `native is None`이면 시각 객체만 있는 쪽이 `_page_diag("scanned", ocr_available=max_ocr_pages > 0)`로
  기록된다. `max_ocr_pages` 기본값은 5(`extract.py:186`)이므로 `ocr_available`이 **참**이 된다.
  이 경로에는 `break`도 `next_continuation`도 없다.
- `extract.py:369-373` — `"scanned"`이고 `ocr_available`이 거짓이 아니면 사유가 **`BUDGET_EXHAUSTED`**가 된다.
- `extract.py:461` — 토큰을 만든 적이 없으므로 `continuation: None`.

평가 측 재현(네 조합): native 있음+예산 0 → `OCR_UNAVAILABLE`, native 없음+예산 0 → `OCR_UNAVAILABLE`,
**native 없음+예산 5 → `BUDGET_EXHAUSTED`·토큰 없음**. 운영 수치(`OCR_UNAVAILABLE` 0, `BUDGET_EXHAUSTED` 11,
`SCAN_UNEXTRACTED` 11)와 일치한다.

문제는 라벨만이 아니다. **"예산을 늘리면 읽힌다"는 잘못된 함의를 주고, 평가 측이 TK-208에서 요구한
사유 분포 자체가 이 지점에서 틀렸다.**

**D2. 실행 미완료 쪽이 있는데 토큰이 없으면 그 파일은 영구히 재사용된다.**

- `packages/rag_engine/library.py:486-489` — 다시 읽는 조건이 `prior["continuation"]`이 참일 때뿐이다.
  거짓이면 `row`가 남아 `files_reused += 1`, `entry["reused"] = True`가 되고 재추출이 일어나지 않는다.
- `library.py:612`는 `parsed` 전체를 저장하므로 토큰 유실은 아니다. **애초에 만들어지지 않았다.**

평가 측 재현(2회 동기화): 1차 내려받기 1·추출기 1회·`INDEXED_PARTIAL`·`BUDGET_EXHAUSTED: [2]`·토큰 없음
→ 2차 **추출기 추가 호출 0회**·`reused: True`·같은 미완독 쪽. 운영 관찰과 같다.

**파급:** 그 자료가 영구 `PARTIAL`이면 `H-REF`가 영원히 불통과이고 **Drive가 `READY`에 도달할 수 없다.**
완독 스냅샷 기준 23항목 비교가 두 회차 연속 불가였던 것이 이 결함의 결과다.

### 고칠 것

**(1) D1 — OCR을 시도조차 못 한 두 경우를 가른다.**

`extract.py:266`의 진단에 `ocr_available`을 `(max_ocr_pages > 0 and native is not None)`으로 두고,
막힌 사유를 하위 필드로 남긴다(예: `ocr_blocked = "NATIVE_RENDERER_UNAVAILABLE"` / `"OCR_BUDGET_ZERO"`).
그러면 `extract.py:369-373`의 기존 분기가 그대로 `OCR_UNAVAILABLE`로 보낸다. **새 사유 값을 만들지 않는다**
(사유 집합은 화면 라벨·탐침·문서에 걸쳐 있다).

**(2) D2 — 미완독 쪽을 세 갈래로 가른다 (2026-11-19 사용자 결정 A).**

| 갈래 | 무엇 | 완독 판정 | 다음 동기화 |
|---|---|---|---|
| (가) 재시도로 읽힌다 | 진짜 예산 소진(토큰 있음), 읽기 시간 초과 | 완독 아님 | **이어 읽는다** |
| (나) 설정을 바꾸면 읽힌다 | OCR 예산 0 (`OCR_BUDGET_ZERO`) | **완독 아님** | 설정 변경 전까지 그대로 |
| (다) 이 자료·이 도구로는 못 읽는다 | 렌더러가 파일을 못 염, OCR을 실제로 돌렸으나 품질 미달 | **'확인된 미독'으로 분리해 완독을 막지 않는다** | 재시도하지 않는다 |

- (나)를 완독으로 보면 **설정 실수가 '완독'으로 읽힌다.** TK-208 1차 판정의 F1이 막은 거짓 녹색이
  그대로 돌아온다. 기존 시험 `test_tk208_scanned_with_zero_ocr_budget_is_execution_incomplete`가
  이 경계를 지킨다 — **그 시험을 고치지 말 것.**
- (다)는 즉시 종결하지 말고 **한 번은 재시도**한 뒤 같은 결과면 확정한다(일시적 실패와 구분).
- (가)는 토큰이 없어도 다시 읽어야 한다. `library.py:486-489`의 재읽기 조건에 '재시도 가능한 미완독
  쪽이 있음'을 더하고, **같은 결과가 반복되면 멈추도록 시도 횟수를 둔다**(무한 재다운로드 금지).

**(3) 표시 — 이것이 빠지면 (다)는 거짓 녹색이 된다.**

- 자료 상태와 라이브러리 상태에서 **진짜 완독과 '읽을 수 있는 것은 다 읽음 + N쪽 확인된 미독'을
  구분할 수 있어야 한다.** 평가 측 사전 검증에서 후보 구현이 둘 다 `INDEXED`·`READY`가 되어
  구분이 사라지는 것을 확인했다. 별도 표식(상태 값 또는 전용 필드)을 둔다.
- 사용자 화면·보고서에 **"자료 N건의 M쪽은 읽을 수 없습니다"와 사유별 건수**를 적는다.
  Drive 파일 식별자·파일명·본문은 적지 않는다.

**(4) 운영 원인 기록.** `pypdfium2.PdfDocument(path)`가 실패한 예외 종류·메시지를 진단에 남긴다
(`extract.py:193`의 `except Exception: pass`가 지금은 통째로 삼킨다). 운영의 그 4개 파일에서 왜
`native`가 `None`이었는지는 평가 측이 오프라인에서 알 수 없다.

### 평가 측 사전 검증 (저장소 밖 사본에 후보를 적용해 돌렸다)

| 검증 | 결과 |
|---|---|
| D1 네 조합 | native 없음+예산 5가 `OCR_UNAVAILABLE`(+`ocr_blocked=NATIVE_RENDERER_UNAVAILABLE`)로 바뀜. 예산 0인 조합은 그대로 |
| D2 경계 | 예산 0 → `coverage_complete=False` (F1 보호 유지). 렌더러 불가 → `coverage_complete=True` + 확인된 미독 쪽 기록 |
| 끝에서 끝까지 | 2회 동기화에서 자료 `INDEXED_PARTIAL` → `INDEXED`, 사유 `BUDGET_EXHAUSTED` → `OCR_UNAVAILABLE`, **라이브러리 `PARTIAL` → `READY`** |
| 기존 시험 | `tests/test_tk208_drive_reference_full_read.py` 6건 전부 통과 |
| 사전 검증이 찾은 빈틈 | 후보 구현에서 자료 상태가 그냥 `INDEXED`가 되어 진짜 완독과 구분되지 않았다 → (3)의 요구로 반영 |

### 수용 기준

1. native를 열지 못한 쪽이 `OCR_UNAVAILABLE`로 분류되고 하위 사유가 기록된다(합성 시험)
2. OCR 예산 0인 쪽은 **여전히 완독이 아니다**(기존 시험 그대로 통과)
3. 재시도 가능한 미완독 쪽은 토큰이 없어도 다음 동기화에서 다시 읽힌다. 같은 결과가 반복되면 멈춘다
4. 확인된 미독 쪽이 있는 자료·라이브러리가 **진짜 완독과 구분되는 표식**을 갖는다
5. 화면·보고서에 미독 자료 수·쪽 수·사유별 건수가 표시된다(캡처 제출). 식별자·본문 없음
6. `pypdfium2` 실패 예외가 진단에 남는다
7. RAG 기존 시험 통과, 시험 삭제·약화 없음, 건너뛰기·`xfail` 없음

## TK-216 — RAG 단계 실패가 건강 판정에 드러나지 않는다

### 문제

2회차 첫 ON 실행이 `rag_status: UNVERIFIED` · `rag_reason: REFERENCE_REVIEW_FAILED` ·
`rag_error_class: OperationalError`로 끝났는데 **`H-ENGINE`은 통과했다.** 표준 23항목은 21/23,
지지·무관 대조는 3/5였다. 같은 ON 설정에서 즉시 재실행하면 정상 완료됐다(23/23).

참고자료 검토가 실패했는데 건강이 녹색이면 사용자가 그것을 알 수 없다. **TK-208의 F1과 같은 종류의
거짓 녹색이고, 건강 판정의 거짓 녹색은 모든 온라인 판정의 근거를 흔든다.**

### 할 일 — 둘로 나뉜다

**(1) 건강 판정이 RAG 실패를 반영한다 (원인과 무관하게 지금 고칠 수 있다, 1차 수용 기준)**

- `rag_status`가 `UNVERIFIED`이거나 `rag_reason`이 `REFERENCE_REVIEW_FAILED`면 `H-ENGINE` **불통과**
- 사용자 화면에 실패 사유와 미검토 범위를 적는다. '검토했으나 근거 없음'과 '검토 자체가 실패'를 구분
- `H-REF`를 포함한 다른 건강 항목의 판정은 바꾸지 않는다
- 합성으로 RAG 단계 예외를 일으켜 `H-ENGINE`이 불통과로 바뀌는 것을 시험으로 고정한다

**(2) `OperationalError`의 자리와 원인**

서버 측 예외 위치·로그를 확인해 DB 세션·연결 풀·작업자 재시작 가운데 무엇인지 가린다. 설정 전환
(TK75 ON/OFF)과 진행 중 작업의 경쟁 상태가 있는지 본다. **가려지기 전에 추측으로 고치지 않는다.**
운영 기록에 설정 변경 중 시작한 사전 실행 1건이 `EXECUTION_SETTINGS_CHANGED`로 실패한 것이 있으나
그 실행은 점검에서 제외된 별건이다.

### 수용 기준

1. RAG 단계 실패가 `H-ENGINE` 불통과로 드러난다(합성 시험)
2. 화면에 실패 사유와 미검토 범위가 적힌다
3. 다른 건강 항목 판정이 바뀌지 않는다(기존 시험 통과)
4. `OperationalError`의 자리가 특정되고 그에 맞는 수정이거나 '원인 미특정'이 명시된다

## TK-218 — 발췌 선택의 관측 공백 (관측만, 선택 로직 금지)

### 문제

2회차에서 목표 자료 발췌가 `387/387자`·오프셋 `0–387`로 전달되고 모델이 응답했으나 `SUPPORTS`가
0건이었다. 그런데 **입력이 충분했는지를 판단할 자료가 없다.**

- `relevance.PER_FILE_EXCERPTS = 3` — 파일당 3건까지 전달 가능한데 1건이 왔다
- 청커는 목표 1,040자·최대 1,200자이고 페이지 전체가 1,200자 이하면 그 페이지가 한 청크다
  (`extract.py:46,62-63`). 387자는 387자 분량의 쪽이다
- 더 긴 청크가 있었는데 떨어진 것인지 387자가 전부였는지가 **어디에도 기록되지 않는다**

'모델이 판단을 못 했다'와 '모델에게 줄 것이 없었다'를 구분할 수 없고, 그 구분 없이는 TK-209의
`(가)` 모델 판단 축을 다룰 근거도 세울 수 없다.

### 고칠 것 — 관측만 더한다

`select()`의 결정 로그와 `review.support_diagnostics`에 다음을 더한다. **본문·파일명·식별자는 적지 않는다.**

1. 파일별 후보 청크 수(임계값 통과/미달), 통과한 것들의 **길이·쪽 번호**
2. 전달된 발췌가 그 파일에서 몇 등인지, `text_coverage`·`shared_terms`, 더 긴 청크가 떨어졌다면 그 사유
   (임계값 미달 / `PER_FILE_EXCERPTS` 초과 / 중복 지문 억제 / 전역 상한)
3. 그 파일의 청크 길이 분포 요약(최소·중앙·최대)

### 하지 말 것

- 선택 점수·임계값·`PER_FILE_EXCERPTS`를 **바꾸지 않는다**
- `RAG_REVIEW_SYSTEM_PROMPT`·관계 판정 기준을 건드리지 않는다. 모델에 '지지 의견을 내라'는 편향
  지시는 거짓 지지를 만든다(거짓 모순과 같은 무게)
- 발췌 본문을 진단에 복사하지 않는다

### 평가 측이 세웠다가 버린 가설 (같은 길로 가지 말 것)

'길이 정규화가 없으니 짧은 제목 쪽이 판시를 담은 긴 쪽을 점수에서 이긴다'고 보았다.
`relevance.coverage()`가 청크 길이로 나누지 않는 것은 사실이다(`relevance.py:195-198`). **그러나 반증됐다** —
합성 재현에서 제목 쪽 153자와 판시 쪽 584자를 같은 질의어로 두니 **판시 쪽이 1등**이고 제목 쪽이
2등으로 둘 다 전달됐다. `coverage()`는 질의어 포함 정도를 보므로 짧은 쪽이 오히려 불리하다.

### 수용 기준

1. 선택된 파일마다 후보 청크 수·길이·쪽·길이 분포가 기록된다
2. 전달된 발췌의 순위와 더 긴 청크가 떨어진 사유가 기록된다
3. 기록에 본문·파일명·식별자가 없다(합성 시험)
4. **선택 결과가 바뀌지 않는다** — 같은 입력에서 전달되는 발췌 집합이 수정 전과 동일함을 합성 시험으로 보인다
5. `RAGC-S1`·`S2`·`N1`·`N2` 영향 없음, RAG 기존 시험 통과
