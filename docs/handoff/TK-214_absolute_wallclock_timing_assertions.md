# TK-214 절대 벽시계 한계를 쓰는 선형 시간 시험이 공용 실행기에서 흔들린다 (평가 측 시험 자산)

- 발견일: 2026-11-19 (평가 세션, PR #342 3차 CI)
- 종류: **시험 자산 불안정.** 제품 결함이 아니다
- 성격: **TK-142가 이미 고친 결함 유형이 다른 파일에 남아 있는 것.** 새 유형이 아니다
- 상태: open

## 증상

`tests/test_tk76_incons_c_eval.py::test_linear_time_on_20k_chars`가 PR #342 CI에서 실패했다.

```
AssertionError: Too slow on 20k chars: 0.751s
assert 0.7507507689999784 < 0.5
```

같은 커밋 `c8376c31`의 다른 CI 실행에서는 같은 잡이 통과했다(TK-212의 중복 실행).

| 실행 | 결과 |
|---|---|
| 44439945603 | success (02:02:11) |
| 44439940978 | **failure** (02:03:51) |

CI 로그의 `CI_TIMER_DIAGNOSTIC`도 `observer_overhead_and_GC_scheduling_perturbation_possible: true`를 적고 있다.

## 평가 측 측정 — 한계의 1/10 아래

같은 입력·같은 코드로 7회 측정했다(평가 환경, python 3.11.18).

| 대상 | 측정 7회(초) | 중앙값 | 최대 |
|---|---|---|---|
| #342 head `c8376c31` | 0.053 0.041 0.040 0.042 0.042 0.040 0.037 | **0.041** | 0.053 |
| `extractor.py`만 base로 되돌림 | 0.045 0.032 0.038 0.032 0.033 0.035 0.032 | **0.033** | 0.045 |

한계 0.5초의 **1/10 아래**다. 평상시 여유가 10배를 넘는데도 공용 실행기 부하에서 0.751초가 나왔다.
즉 이 단언은 **코드의 성능이 아니라 실행기의 부하를 재고 있다.**

## 원인 — 절대 벽시계 한계

```python
def test_linear_time_on_20k_chars():
    """2만 자 악성 입력 선형 시간 검증."""
    ...
    t0 = time.perf_counter()
    _ANAPHORA_EVENT_RE.findall(evil_1)
    _UNIQUENESS_MARKER_RE.findall(evil_2)
    check_internal_inconsistency(_doc(evil_1))
    elapsed = time.perf_counter() - t0
    assert elapsed < 0.5, f"Too slow on 20k chars: {elapsed:.3f}s"
```

한 점(2만 자)에서 한 번 재고 절대 시간과 비교한다. 선형성을 보려는 시험인데 **점이 하나라 기울기를
구할 수 없고**, 부하가 그 한 번에 몰리면 실패한다.

## 이미 있는 처방 — TK-142

**TK-142**(2026-11-03 사용자 결정, #215 `c1c5994` 수용, Steve 병합 `0d7051b`)가 같은 성격의 흔들림을
`tests/test_pii_redos_linear.py`에서 고쳤다. 그 티켓의 2절을 그대로 옮긴다.

> 같은 엄격도: 길이 4배에 비 8 = 증가 지수 log 8 / log 4 = **1.5**. 그대로 둔다.
> 측정을 바꾼다: 길이 2,000·4,000·8,000·16,000 네 점, 5회 교차 측정(길이를 번갈아 재서 부하가
> 한 길이에만 몰리지 않게), 길이별 최솟값의 log-log 최소자승 기울기 < 1.5.
> 기존 절대 상한(8,000자 2초)은 유지.
> 측정 방법 자체의 시험 추가: 제곱 시간 작업은 지수 > 1.5, 선형 작업은 < 1.5.

사전 검증 결과도 그 티켓에 있다: CPU 4코어 포화 부하 12회에서 기존 실패 3 → 변경안 실패 0.

**그 처방이 `test_tk76_incons_c_eval.py`에는 적용되지 않았다.** 같은 결함이 다른 자리에 남아 있다.

## 할 일 (평가 측)

1. **전수 조사 먼저.** 저장소의 시험 가운데 절대 벽시계 한계로 단언하는 자리를 모두 찾는다.
   한 자리만 고치면 다음에 다른 자리가 깨진다. `time.perf_counter()`·`time.time()` 차이를 상수와
   비교하는 모든 단언을 목록으로 만든다.
2. **TK-142 처방을 적용한다.** 여러 길이 × 교차 측정 × log-log 기울기. 엄격도를 낮추지 않는다.
   절대 상한은 **여유를 크게 둔 상한**(예: 평상시 중앙값의 수십 배)으로만 남겨 ReDoS 폭주를 잡는다.
3. **측정 방법 자체의 시험을 함께 둔다.** 제곱 시간 작업에서 지수가 한계를 넘고 선형 작업에서
   넘지 않는 것을 단언한다(TK-142가 그렇게 했다).
4. **부하 재현으로 검증한다.** CPU 포화 부하에서 반복 실행해 기존 실패 수와 변경안 실패 수를 적는다.

## 수용 기준

1. 절대 벽시계 한계 단언이 저장소에서 남지 않는다(전수 조사 목록과 함께 보인다)
2. 엄격도가 낮아지지 않는다 — ReDoS 수정 전 탐지기에서 여전히 실패로 잡힌다
3. 측정 방법 자체의 시험이 있다
4. CPU 포화 부하 반복에서 변경안 실패 0
5. 시험 이름 유지, 단언 수 감소 없음, 건너뛰기·`xfail` 없음

### 부하 검증 결과 — **수용 기준 4 미달** (중요)

| 사본 | 8회 중 실패 |
|---|---|
| 옛 사본(단발 측정) | **4** |
| 새 사본(최솟값·기울기) | **3** |

그리고 더 중요한 사실이 드러났다.

> **지속적 포화 부하에서는 N회 최솟값이 빡빡한 절대 한계를 구하지 못한다.**
> 부하가 모든 회차를 똑같이 늦추므로 최솟값도 함께 늦어진다. 최솟값은 **일시적 스파이크**에만
> 듣는다. 균일한 감속에 면역인 것은 **상대적 측도**(기울기·비율)뿐이다.

즉 1안은 느슨한 한계(1초·10초·30초)에는 충분하지만 0.1초급에는 부족하다. `test_tk76`처럼
기울기로 바꾼 자리는 부하에서도 깨지지 않았다(상대 측도이므로).

## 2차: 자가 보정 상대 한계 (2026-11-19 사용자 결정 1안)

사용자 결정 원문: **"1"** (= 자가 보정 상대 한계).

### 왜 최솟값만으로는 안 됐나

1안 적용 뒤 부하 검증에서 0.1초급 단언이 여전히 깨졌다. **지속적 포화 부하는 모든 회차를
똑같이 늦추므로 최솟값도 함께 늦어진다.** 최솟값은 일시적 스파이크에만 듣는다.

### 보정 설계 — 값은 전부 측정해서 골랐다

같은 실행 안에서 기준 작업을 재어 이 기계·이 순간이 기준보다 몇 배 느린지 구하고 한계를
그만큼 늘린다. 기계 속도와 부하가 약분되므로 엄격도는 유지된다 — ReDoS 폭주는 100~1000배이고
배수 상한은 50이다. **대상 작업을 반복하지 않고 기준 작업만 반복하므로**, 상태가 쌓이거나
동시성을 함께 재는 자리(앞서 '반복 불가'로 분류한 5자리)에도 쓸 수 있다.

| 고른 것 | 근거 (평가 측 실측) |
|---|---|
| 통계 = **평균** | 기준 20,000회에서 최솟값 0.000825초(배수 0.99) 대 평균 0.002479초(배수 2.96). 짧은 작업의 최솟값은 빈 타임슬라이스에 끼어들어 부하와 무관하게 빠르다 |
| 기준 크기 = **200,000회** | 20,000 / 200,000 / 1,000,000회를 부하 없음·포화에서 재어 비교: 배수 3.44·2.29·2.70, 흔들림 1.11·1.07·1.05배, 비용 0.006·0.050·0.150초 |
| **준비 회차 폐기** | 없으면 한가한 기계에서도 배수 1.753(첫 호출 적재 비용이 평균에 섞인다). 폐기 뒤 7회 모두 1.000 |
| 캐시 20초 | 자리마다 다시 재면 시험 전체가 그만큼 길어진다 |
| 배수 하한 1.0 | 더 빠른 기계에서 한계가 조여지면 거짓 실패가 난다 |
| 배수 상한 50 | 병적으로 느린 환경에서 단언이 무력해지지 않게 |

첫 구현이 최솟값을 써서 '0.1481초 > 보정 한계 0.1000초(감속 배수 1.00)'로 실패했고,
그 실패가 통계 선택의 근거가 됐다.

### 비율 단언 10자리는 되돌렸다

기계적 적용이 `ratio < 8.0` 같은 **무차원 비율**에도 보정을 걸었다. 비율의 한계를 감속 배수로
늘리면 **엄격도가 오히려 떨어진다** — 비율은 이미 상대 측도이고 부하에 면역이다.
자체 검토에서 잡아 되돌렸다.
