# TK-95 TK-71 시간 상한 시험이 CI 러너 속도에 따라 실패한다 (P2, 시험 견고성, 기존 결함)
- 유형: 시험 견고성(CI 불안정). 탐지·채점 규칙 변경이 아니다.
- 발견: 평가 측, 2026-10-21 #153 병합 시도 중. 저장소 규칙이 필수 검사 실패로 병합을 거부했다.

## 1. 증상
- `tests/test_tk71_structured_case_table.py`의 시간 상한 시험 두 개가 PR과 무관하게 번갈아 실패한다. 둘 다 벽시계 기준 `elapsed < 0.1`이다.
  - `test_case_number_normalization_repeated_input_is_bounded`(72행): 값 5,000개 정규화. CI 실측 0.60~0.66초.
  - `test_row_security_prefilter_repeated_input_is_bounded`(87행): CI 실측 0.66초.
- 같은 시험이 같은 head의 다른 실행에서는 성공한다. 평가 측 로컬(Steve `ea97fce`)에서도 3회 모두 통과했다.
- 10-19 이후 실패를 확인한 곳(CI 결과 인용): #149, #152(PR 실행), #154(push 실행), #159(PR 실행), #153(두 실행 연속, 재실행 포함).
- 이 시험이 대상으로 하는 코드(`packages/rag_engine/case_table.py`)는 위 PR들이 바꾸지 않았다.
- 필수 검사 '테스트 (SQLite + PostgreSQL/pgvector + Redis)'는 SQLite 잡이 실패하면 함께 실패한다. 그래서 시험만 불안정해도 병합이 막힌다.

## 2. 요구
1. 시험의 **목적(입력 길이에 비례하지 않는 폭증, 즉 제곱 증가를 잡는 것)은 유지**한다. 시험을 건너뛰기·비활성화·xfail로 만들지 않는다.
2. 벽시계 절대 상한 대신 러너 속도에 덜 민감한 기준으로 바꾼다. 예:
   - 같은 시험 안에서 길이 1배·4배를 각 3회 재고, 최솟값 비가 8 미만인지 본다(점검표 2항과 같은 방식).
   - 절대 상한이 꼭 필요하면 최솟값 기준으로 바꾸고, 근거와 함께 여유를 둔다.
3. 같은 파일의 다른 시간 시험(127행 등)과 저장소의 다른 시간 상한 시험 가운데 같은 꼴(단일 측정, 0.1초 수준 절대 상한)을 목록으로 찾아 같이 정리한다.
4. 기존 시험을 바꾸는 것이므로 '전에 확인하던 요구 → 새 확인 방식' 대응표를 PR에 낸다. 평가 측이 `approved_test_marks.json`에 승인을 올린다.

## 3. 시험·수용
- 바꾼 시험을 로컬에서 30회 반복해 통과율을 낸다.
- 의도적으로 제곱 증가를 넣은 합성 구현(시험 안 지역 함수)에서는 새 기준이 실패하는지 보여 준다. 즉 감시 능력이 유지됨을 입증한다.
- 탐지 diff 0. CI 필수 검사 성공.
