# TK-88 검토 화면 3단 체계: AI 작성 → 판례·법령·주요참고문헌 인용 오류·미확인 → 법률적으로 무리한 주장 (P2, 기능 구조, 사용자 개선안 3다·4, 설계 메모 먼저)
- 근거: 사용자 개선안(2026-10-19) 3다·4항과 평가 측 조정안(HISTORY 10-19).

## 1. 현재
- 엔진은 출처 확인(공식 DB 조회)과 법리 타당성 판정(법리 검토 모델)을 따로 낸다. 그런데 확인할 항목 표에서는 한 줄에 섞인다(`app.js` 1650·1919행, `packages/verification_engine/review_items.py` 230~238행).
- 주요 참고문헌(RAG) 결과는 표 아래 별도 구역(`app.js` 728~800행)에 접힌 채 있다. 참고자료 '모순'만 TK-70으로 표에 올라온다.
- 주장·쟁점 탭은 쟁점·요건사실·주장별 인부·지지 상태 입력을 보여 준다(`workflow.js`).

## 2. 목표 구조
| 단 | 탭·제목 | 담는 것 |
|---|---|---|
| 1 | AI 작성·보안 진단 | 현행 유지 |
| 2 | **판례·법령·주요참고문헌 인용 오류·미확인 검토 (AI 작성 여부 판단과 별개)** | 인용한 판례·법령·참고문헌을 찾지 못함, 사건번호·서지 불가능(예: 성립 불가 사건번호), 인용 문구가 원문과 다름 |
| 3 | **법률적으로 무리한 주장** (현 주장·쟁점 탭 자리) | 출처는 확인되나 주장이 판례·법령 취지와 맞지 않음(법리 검토 '부당'), 참고자료 내용과 모순(TK-70) |

## 3. 설계 메모에 담을 것 (승인 전 구현 금지)
1. 분류 규칙: 결과 유형·판정별로 2단/3단을 정하는 표. 한 인용에서 두 단의 결과가 함께 나오면 어떻게 보이는지.
2. 참고문헌 표시 조건(법률 측면):
   - 업무편람·실무제요 등은 실무 해설서이며 법적 구속력이 없다. 판례·법령과 같은 표에 두더라도 '참고문헌(구속력 없음)' 표시를 붙이고, 위험 지수 제외(`gate.py` 159·238행)를 유지한다.
   - '불부합 없음'을 '부합'으로 표시하지 않는다. 색인 범위(운영 10-19 기준 31건 중 5건), 주장별 대조 상한, 문서 앞 12,000자 기준 때문에 '대조 안 함'과 '부합'을 반드시 나눈다.
3. 표 아래 RAG 구역의 처리: 동기화 상태·자료별 처리 기록은 접힌 '참고자료 연결 상태' 한 줄로 줄이고, 주장별 대조 의견은 해당 행으로 옮긴다.
4. 주장·쟁점 탭의 기존 입력(쟁점 편집·인부·지지 상태)을 어떻게 정리하는지(TK-87과 같은 원칙).
5. 결과 JSON·보고서의 구조 변경 여부. **채점기와 `match_spec`은 바꾸지 않는다.** 결과 유형·등급·상태를 바꾸지 않고 화면 배치만 바꾸는 것을 원칙으로 한다.

## 4. 수용
- 탐지 diff 0, 고정·은퇴 점수 불변(동일 조건 대조). 결과 유형·등급이 바뀌면 그 자체로 불수용이다.
- 실제 진입점 시험: 2단·3단에 각각 들어가야 할 합성 결과가 제자리에 보이고, 참고문헌 행에 '구속력 없음'·'대조 안 함' 표시가 나온다.
