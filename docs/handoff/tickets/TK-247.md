## 1. 문제 현상
- 0.30.1 배포 뒤 첫 검증 실행(2026-11-27 01:44 UTC, 평가 측 OCR 프로젝트)에서 재처리 판 v2(`tk245-fallback-env-v2`)가 저품질 쪽이 있는 Drive 파일 **7개**(저품질 16쪽)의 재처리를 일으켰다.
- 7개 모두 다시 내려받아(29.6 MB) 추출하다가 **각 30초 한도에 걸려 실패**했다(추출 7회 합계 210초, `REFERENCE_PARSE_TIMEOUT`).
- 실패한 빈 결과가 기존 정상 추출본을 **덮어쓴 채 저장**됐다. 이후 모든 실행이 그 빈 결과를 재사용하며 다시 시도하지 않는다.

| 라이브러리 상태·색인 | `READY`, 41/41 | **`PARTIAL`, 34/41** |
| 손상 파일 | — | 7개(연구논문·법령해석·판례 폴더), 검색 가능 쪽 **411·772·323·177·213·455·248 → 모두 0**(합계 2,599쪽) |
| 파이프라인 건강 명세 | 6/6 | **5/6**(`H-REF` 실패: 동기화 오류, `REFERENCE_PARSE_TIMEOUT` 7) |

## 2. 원인 (`55efe21a` `packages/rag_engine/library.py`, 평가 측 재현으로 확인)

1. **재처리 시간 한도가 첫 추출과 같다.** `:965` `kwargs = {"directory": self.directory, "timeout": 30}`. 재처리는 파일 전체를 다시 내려받아 다시 추출한다(`:886` `reprocess_low_quality`는 `:933-935` 로컬 캐시 재사용 대상도 아니다). 0.30.1부터 하위 프로세스에서 RapidOCR 폴백이 실제로 돌아(모델 적재 + 쪽당 수 초, Render `starter` 0.5 CPU) 수백 쪽 파일이 30초를 넘긴다.
2. **실패하면 기존 결과를 버린다.** `:989` `parsed = {"chunks": [], "partial": True, "reason": str(exc)}`. 그 뒤 `:1096-1099`(`Cache terminal parse outcomes`)가 `DELETE FROM chunks` 후 빈 결과를 저장한다. 재처리는 '더 낫게 만들기'인데 실패가 정상본을 지운다.
3. **허위 복구 집계.** `:1063` `recovered_pages = max(0, prev_low_pages - cur_low_pages)`. 빈 결과에는 저품질 쪽이 없으므로 `cur_low_pages = 0` → 실패한 쪽이 모두 '복구'가 된다.
4. **재시도·복원 경로 없음.** `:1064-1065`가 실패해도 `low_quality_reprocess_version = v2`를 기록해 재처리를 끝낸다. 빈 결과(`reason=REFERENCE_PARSE_TIMEOUT`, `chunk_count=0`)는 `_has_retryable_unread`(`:842`) 등 어느 재시도 조건에도 걸리지 않아 **영구히 재사용**된다.

**재현(평가 측 사본 `55efe21a`, 제품 `ReferenceLibrary.sync` + 시험 하네스의 가짜 Drive, 정상 400조각·407쪽·저품질 4쪽 파일, 추출기는 시간 초과):** 1회차 실행에서 조각 400 → **0**, 상태 `PARSE_FAILED`, `recovered_pages` **4(허위)**, 판 v2 기록. 2·3회차는 추출 없이 빈 결과 재사용. 운영 관측과 같다.

## 3. 고칠 것

1. **재처리 실패 시 기존 결과 보존.** 재처리류(`reprocess_low_quality`·`retryable_unread`·`confirm_unreadable`·`legacy_unread_reeval`) 추출이 `REFERENCE_PARSE_TIMEOUT`·`REFERENCE_PARSE_FAILED`로 끝나고 기존 결과에 본문(`chunk_count>0` 또는 `searchable_pages>0`)이 있으면:
   - 기존 조각과 기록을 지우지 않는다(조각 삭제·삽입 생략, 기록만 갱신).
   - 이번 실행에서도 기존 결과로 색인한다(사용 불가로 빼지 않는다).
   - `reprocess_failures`(+1)·`last_reprocess_error`를 기록하고 `recovered_pages=0`으로 둔다.
   - **두 번 실패하면** 그 판의 재처리를 멈춘다(판 기록). 한 번 실패하면 다음 실행에서 한 번 더 시도한다.
2. **재처리 전용 시간 한도.** 재처리류는 첫 추출(30초)과 분리된 한도를 쓴다. 사전 검증값은 다음과 같다. 값은 구현 측이 운영 측정으로 정해 PR에 근거를 적는다.
   - `LV_REFERENCE_REPROCESS_TIMEOUT` 기본 120초
   - 실제 한도 = `min(120, 남은 동기화 예산 − 60)`
3. **예산이 부족하면 재처리를 미룬다.** 위 한도가 30초 미만이면(남은 예산 90초 미만) 기존 결과를 쓰고 재처리는 다음 실행으로 미룬다(`reprocess_deferred` 기록). 재처리가 예산(300초)을 다 써서 **뒤의 캐시 파일까지 그 실행에서 색인 밖으로 밀리는 것**을 막는다(`SYNC_BUDGET_EXHAUSTED` 분기가 뒤 파일을 `SELECTED_PENDING`으로 돌린다).
4. **이미 손상된 파일 자동 복원(운영 7개).** 저장 기록이 `reason ∈ {REFERENCE_PARSE_TIMEOUT, REFERENCE_PARSE_FAILED}`이고 `chunk_count=0`이며 이어 읽기 중이 아니면 `restore_failed_extract`로 다시 추출한다.
   - **폴백을 끈 1차 OCR만으로** 추출한다(0.30.0에서 같은 파일이 30초 안에 성공하던 경로).
   - `restore_attempts`로 최대 2회까지만 시도한다(손상 표식은 `previous_searchable_pages>0` 또는 `restore_attempts>0`). **처음 추출부터 시간 초과가 난 파일은 대상이 아니다** — 기존 시험 `tests/test_drive_rag.py::test_terminal_parse_timeout_does_not_starve_later_files`(큰 파일이 뒤 파일을 굶기지 않게 재시도하지 않음)를 지킨다.
   - 복원에 성공하면 재처리 판 기록을 지워, 다음 실행에서 폴백 재처리를 1항 보존 규칙 아래에서 한 번 더 시도하게 한다.
5. **집계.** 실패한 재처리는 복구로 세지 않는다. 매니페스트에 `reprocess_failed`·`reprocess_deferred`·복원 건수를 노출한다. 건강 명세 `H-REF`가 손상을 계속 드러내도록 사유를 유지한다.
6. **배포 뒤 확인.** 운영 첫 실행에서 7개 파일이 복원되어 색인 41/41로 돌아와야 한다. 평가 측이 온라인 재측정으로 확인한다.

## 4. 사전 검증 (평가 측 사본 `55efe21a` + 위 1~5, 저장소 밖)

**방법:** 제품 `ReferenceLibrary.sync`, 시험 하네스와 같은 가짜 Drive(`tests/unit/test_tk245_drive_ocr_fallback_env.py` 방식). 파일은 정상 400조각·407쪽·저품질 4쪽이다. 추출기는 시나리오별로 시간 초과·폴백 켤 때만 시간 초과로 둔다. 각 시나리오에서 동기화를 3회 연속 실행했다.

| 시나리오 | 배포 코드 | 수정 사본 |
|---|---|---|
| 재처리가 항상 시간 초과 | 1회차 조각 400→**0**, `PARSE_FAILED`, 허위 복구 4, 이후 재시도 없음 | 1·2회차 시도(한도 120초) 모두 실패해도 **조각 400·407쪽 유지, `READY` 색인 1/1**, 복구 0, 2회 실패 뒤 정지 |
| 폴백 켤 때만 시간 초과 | 위와 같음 | 위와 같음(보존) |
| **이미 손상된 파일**(운영 현재 상태) + 폴백 켤 때만 시간 초과 | 추출 없이 빈 결과 영구 재사용 | 1회차 **폴백 끄고 복원 → 조각 400·407쪽, `READY`**. 2회차 폴백 재처리 시도 → 실패 → 보존. 3회차 다시 실패 → 정지. 내내 400조각 유지 |
| 이미 손상된 파일 + 항상 시간 초과 | 영구 재사용 | 복원 2회 시도(`restore_attempts` 1→2) 후 정지(손상 그대로, `PARSE_FAILED` 유지 — 더 나빠지지 않음) |
| 남은 예산 100초 | — | 한도 40초로 재처리 시도(실패해도 보존) |
| 남은 예산 60초 | — | 추출 0회(미룸), 기존 결과 재사용, 색인 유지 |

- 관련 기존 시험(Drive 라이브러리·격리 추출·재처리를 쓰는 33개 파일): **전부 통과**(배포 코드 사본과 같은 결과).
- **사전 검증 중 고친 지시의 빈틈 2건:**
  - ① 처음에는 복원 대상을 '빈 결과 전체'로 잡았다. 그러자 기존 시험 `test_terminal_parse_timeout_does_not_starve_later_files`가 실패해, 대상을 '재처리로 손상된 파일'로 좁혔다.
  - ② 처음에는 예산 미룸 기준을 '한도 + 60초 미만'으로 잡았다. 그러자 남은 예산 100초를 쓰는 기존 시험 3건(`test_tk237_pos3`·`test_tk245_pos2`·`test_tk245_pos3`)에서 재처리가 미뤄져 실패해, 한도를 '남은 예산 − 60'으로 바꿨다.
- 평가 측 수정 사본 diff(참고, 63+줄): 저장소 밖 보관. 구조는 위 1~5절과 같다.
- **미검증:** 실제 Drive 7개 파일의 운영 처리 시간(사용자 비공개 자료 — 평가 측이 내려받지 않는다), 운영 CPU에서 120초 한도의 충분성, 고정·은퇴 세트(오프라인 고정 세트는 Drive를 쓰지 않음).
