## 1. 문제 현상 및 결함 범주
- **현상**: 운영과 같은 RapidOCR 설정(`korean_PP-OCRv5_rec_mobile`, 나머지 기본값)은 **깨끗한 A4 쪽에서도 18줄 중 6~13줄만** 돌려준다. 저장소 정상 스캔 픽스처는 4줄 중 2줄만 읽는다. 저품질 픽스처는 신뢰도 0.526·글자 정확도 0.13으로 `UNVERIFIED`가 된다.
- **범주**: OCR 엔진 설정 결함(폴백 경로). 탐지 결과는 OCR 본문 변화로만 바뀐다.

## 2. 원인 (재현으로 확인, `71a8ffc3` 기준)

1. `packages/document_engine/ocr.py:683-689` `RapidOCRAdapter._ensure_engine()`가 `RapidOCR(params={Rec.* 세 항목})`만 지정한다. 나머지는 패키지 기본값(`rapidocr` 3.10.0 `config.yaml`)이고, 그중 `Global.use_cls: true`가 켜져 있다. 이 설정은 검출한 글줄마다 **방향 분류기**(`ch_ppocr_mobile_v2.0_cls`, 중국어 학습)를 돌려 180° 뒤집힌 줄을 바로 세운다.
2. 이 분류기가 **똑바로 선 한국어 줄 상당수를 '뒤집힘'으로 오판**해 이미지를 돌린다. 인식기는 거꾸로 된 줄을 읽어 잡음이나 낮은 점수를 내고, `Global.text_score: 0.5`(점수 0.5 미만 버림)에 걸려 **줄이 통째로 사라진다**. 남은 줄은 점수가 높아 쪽 평균 신뢰도는 높게 나온다(일부 줄만 읽고도 '정상').
3. 다른 후보를 하나씩 바꿔 원인을 좁혔다(깨끗한 A4 18줄 기준).

| 바꾼 설정 | 결과 |
|---|---|
| 없음(운영) | 6~13줄 |
| `Global.width_height_ratio=-1`, `Global.min_height=0` | 변화 없음 |
| 검출기를 PP-OCRv5 mobile로 | 6~12줄 |
| `Global.text_score=0` | 18줄이 나오지만 평균 0.69~0.70(뒤집힌 줄이 쓰레기 값으로 남음) |
| **`Global.use_cls=False`** | **18줄, 평균 0.967~0.986** |

4. 쪽 단위 방향(90·180·270°)은 이미 `packages/document_engine/pdf_parser.py` `_reoriented()`가 OSD와 회전 후보 비교로 처리한다. 글줄 단위 분류기는 이 경로와 겹치고, 한국어에서는 해만 끼친다.

## 3. 고칠 것

1. `_ensure_engine()`의 `RapidOCR(params=...)`에 **`"Global.use_cls": False`** 를 넣는다. 이유를 주석으로 남긴다.
2. `docker/Dockerfile:22` 사전 다운로드 명령은 이미 `use_cls=False`로 호출하므로 그대로 둔다. 운영 이미지에 분류기 모델이 남아 있어도 쓰지 않는다.
3. **회전된 쪽의 처리를 확인한다.** 쪽 전체가 180° 뒤집힌 입력에서 폴백이 쓰레기 본문을 '정상'으로 채택하지 않아야 한다. 사전 검증에서 분류기를 끄자 뒤집힌 쪽의 '정상' 오판이 17/96에서 1/96으로 줄었다. 남은 1건(짧은 3줄, 한글 비율 미평가)도 시험으로 확인한다.
4. 진단 필드에 RapidOCR 설정(`use_cls`)을 노출한다(`check_ocr_runtime` 또는 폴백 기록). 다음 판에서 기본값이 바뀌어도 드러나게 한다.

## 4. 사전 검증 (평가 측 사본: `71a8ffc3` + TK-243 + TK-244 + TK-244 보완 1회차 + 위 1)

**측정 조건:** 평가 컨테이너 Linux, Python 3.13 가상환경, `rapidocr` 3.10.0, `onnxruntime`, 운영과 같은 `korean_PP-OCRv5_rec_mobile` 모델(2026-11-27 사용자 승인으로 내려받음), tesseract 5.3.4(운영 5.5.0), 200 dpi 렌더링.

### 4.1 저장소 고정 픽스처 (제품 PDF 파서 경로 `PdfParser.parse`)

| 입력 | 배포 코드 | 수정 사본 |

RapidOCR 단독 글자 정확도(공개 합성 정답 대비, `difflib` 비율): 정상 스캔 0.821 → **1.000**, 저품질 스캔 0.130 → **0.756**. 저품질 복구 본문에는 오탈자가 남는다(4줄 중 3줄에 1~2글자). 날짜·수량(연·월·일, 개수)은 정확했다.

### 4.3 관련 기존 시험
- OCR·폴백·전처리·한글 비율을 쓰는 15개 파일: `tests/test_v5_ocr_dates.py::test_rotated_scan_page_impossible_date_is_found` 1건 외 통과. 이 1건은 배포 코드 사본에서도 똑같이 실패하는 기존 환경 요인(평가 컨테이너 tesseract 5.3.4)이다. CI(`Docker OCR readiness`, tesseract 5.5.0)에서 통과해야 한다.
- `use_cls`·`Rec.*` 설정을 직접 단언하는 기존 시험은 없다(저장소 검색).

### 4.4 미검증
- 운영(Render, tesseract 5.5.0)에서의 실제 복구: 배포 후 평가 측 온라인 재측정.
- 고정·은퇴 세트: 오프라인 고정 세트는 텍스트 레이어 문서라 RapidOCR 폴백 경로를 쓰지 않을 것으로 보지만 실행하지 않았다.
- 실제 스캔 문서(사람이 찍은 사진·복사본): 합성 흐림·잡음으로만 쟀다.
- 운영 메모리 한도: 측정 프로세스의 최대 메모리(714~727 MB)가 Render `starter` 한도(512 MB)를 넘는다. 이 수정과 무관하게 **현재 운영에도 있는 조건**이다. 빽빽한 A4 쪽이 폴백으로 갈 때 운영 메모리를 따로 확인해야 한다(아래 6절).

## 6. 사용자 결정 대기 (CLAUDE.md 2026-11-09 예외 (나) — 판정 기준 변경)
분류기를 끄는 것은 지금 기준(평균 신뢰도 0.70)에서도 **모든 측정 축에서 현재보다 낫다.** 다만 폴백이 쓰이는 구간(Tesseract 저품질)에서는 신뢰도 0.70을 넘는데 글자가 많이 틀린 '오복구'가 남는다. Tesseract 시간 초과 칸을 뺀 31칸 기준은 다음과 같다.

| 폴백 채택 쪽의 `OCR_EXTRACTED` 기준 | 복구 | 정확(≥0.8) | 중간(0.6~0.8) | 오복구(<0.6) | 저장소 저품질 픽스처(0.75) |
|---|---|---|---|---|---|
| 0.70(현행 유지) | 18 | 5 | 5 | 8 | 복구됨 |
| 0.75 | 16 | 5 | 4 | 7 | 복구됨(경계) |
| 0.80 | 11 | 5 | 4 | 2 | **복구 안 됨** |
| 0.85 | 7 | 5 | 2 | 0 | **복구 안 됨** |

같은 조건에서 현재 운영(분류기 켬, 0.70)은 복구 10, 정확 0, 오복구 8이다. 기준을 폴백 채택 쪽에만 따로 둘지는 설계 범위 변경이라 사용자 결정 사항이다. 결정 전까지 이 티켓은 3절(분류기 끄기)만 다루고 기준값은 바꾸지 않는다.

**결정(2026-11-27 사용자):** "폴백 채택 쪽 기준값 0.70 유지 결정". 폴백 채택 쪽에도 기준값 0.70(`ocr_quality_min_confidence`)을 그대로 쓴다. 별도 기준을 두지 않는다. 수용 기준 변화 없음.
