# TK-212 PR 하나에 CI 실행이 둘 트리거되어 필수 확인 결론이 엇갈린다 (평가 측 CI 자산)

- 발견일: 2026-11-19 (평가 세션, #339·#341·#343 병합 과정)
- 종류: **평가 측 CI 자산 결함.** 제품 결함이 아니다
- 상태: open

## 증상

PR 하나의 같은 head SHA에 CI 워크플로 실행이 **둘** 걸린다. 한쪽이 취소되거나 다른 기준(base)으로
돌면서 같은 이름의 필수 확인이 서로 다른 결론을 낸다. GitHub 브랜치 규칙은 **더 늦게 끝난 결론**을
세므로, 성공 결론이 있어도 병합이 막히거나 반대로 실패가 가려질 수 있다.

실제로 세 번 막았다.

| PR | 증상 | 결과 |
|---|---|---|
| #339 | 같은 head에 실행 2개. `테스트 (SQLite + PostgreSQL/pgvector + Redis)` 집계 잡이 한쪽에서 `SQLite: cancelled / PostgreSQL: cancelled`를 받아 실패 보고 | 평가 측이 취소임을 가려냄 |
| #341 | `점수 하락 게이트`가 한 실행에서 success(22:57), 다른 실행에서 **cancelled**(23:07). 규칙이 늦은 쪽을 세어 **병합 거부**(`Required status check "점수 하락 게이트" is cancelled`) | 워크플로 재실행으로 해소 |
| #343 | `점수 하락 게이트`가 한 실행에서 success, 다른 실행에서 **failure**. 두 실행의 `BASE`가 달라 `check_test_edits.py`의 기준이 PR base(`556dac84`)와 직전 head(`1d27895f`)로 갈렸다 | 평가 측이 로그를 읽어 점수 하락이 아님을 확인 |

#343의 사례가 특히 나쁘다. **같은 커밋에 대해 게이트가 서로 다른 기준으로 돌아 결론이 갈린다.**
기준이 직전 head면 같은 PR 안의 시험 교체가 '기존 시험 삭제'로 잡힌다.

## 평가 측 확인 (정적)

- `.github/workflows/ci.yml`의 `BASE` 결정은 아래 꼴이다.

      BASE="${{ github.event.pull_request.base.sha }}"   # 또는 event.before
      if [ -z "$BASE" ] || [ "$BASE" = "0000...0" ] || ! git cat-file -e "$BASE^{commit}"; then BASE=HEAD~1; fi

  실행이 `pull_request`로 트리거될 때와 `push`로 트리거될 때 쓰는 값이 다르다. 두 트리거가 모두
  걸리면 같은 head에 기준이 다른 실행이 둘 생긴다.
- 취소는 뒤 커밋이 앞 실행을 밀어낼 때 생긴다. 취소된 필수 확인이 **성공 결론을 덮는다.**

주원인은 **미검증**이다. 트리거 조합(`push` + `pull_request`)과 `concurrency` 설정을 함께 보아야 한다.

## 할 일 (평가 측)

1. **진단.** 같은 head에 실행이 둘 생기는 트리거 조합을 워크플로 파일에서 확정한다. 추정으로
   하나를 고르지 않는다.
2. **중복 제거.** 트리거 종류만 바꾸는 것으로는 풀리지 않는다. PR 브랜치에 푸시하면 `push`와
   `pull_request`가 **둘 다** 발생하므로 같은 head에 실행이 둘 남는다. 반대로 `push`를 넓게
   제외하면 PR이 없는 브랜치의 직접 푸시 CI가 빠져 필수 확인이 누락된다. 그래서 **라우팅 기준을
   명시**해야 한다.
   - `push` 실행은 **PR이 없는 ref에서만** 일을 하게 한다. 잡 수준 `if`로 가른다
     (보기: `if: github.event_name == 'pull_request' || github.ref == 'refs/heads/main' ||
     github.ref == 'refs/heads/Steve_ACASiaLAW'`). 어떤 ref를 `push`로 돌릴지는 보호 규칙이
     필수 확인을 요구하는 ref 목록과 맞춘다.
   - `concurrency` 그룹을 **이벤트 종류가 아니라 head ref 단위**로 두어(`group:
     ci-${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}`)
     같은 head의 두 실행이 서로를 취소하지 않고 하나만 남게 한다.
   - `cancel-in-progress`를 쓰되 **필수 확인을 내는 잡이 취소 상태로 남지 않게** 한다. 취소
     결론이 성공을 덮는 것이 #341에서 병합을 막은 원인이다.
   - 가른 뒤에는 **필수 확인 이름마다 실행이 하나인지** 확인한다. PR 갱신·브랜치 직접 푸시·포크
     PR 세 경우를 각각 본다.
3. **기준 고정.** 게이트의 `BASE`를 **항상 PR base**(`github.event.pull_request.base.sha`)로
   고정한다. 직전 head를 기준으로 쓰면 같은 PR 안의 정당한 시험 교체가 삭제로 잡힌다.
   `push` 실행에서는 `merge-base`를 쓴다.
4. **확인.** 같은 PR에 커밋을 두 번 밀어 실행이 하나만 남고 필수 확인 결론이 하나인지 본다.

## 수용 기준

1. PR 하나의 head SHA에 CI 실행이 하나만 남는다. PR 갱신·브랜치 직접 푸시·포크 PR 세 경우를
   각각 확인해 보인다
2. 필수 확인 이름마다 결론이 하나다(취소 결론이 성공을 덮지 않는다)
2-1. PR이 없는 브랜치의 직접 푸시에서 필수 확인이 빠지지 않는다(중복을 없애려고 `push`를 넓게
   제외하면 이 조건이 깨진다)
3. 게이트의 기준이 PR base로 고정되어 같은 PR 안의 시험 교체가 '기존 시험 삭제'로 잡히지 않는다
4. 기존 CI 단계와 필수 확인 이름은 바꾸지 않는다(브랜치 보호 규칙이 이름으로 걸려 있다)

## 미검증

주원인(트리거 조합·`concurrency`)을 아직 가리지 않았다. 증상은 세 PR에서 재현됐다.

## 수정 (2026-11-19 사용자 결정 B-1)

사용자 결정 원문: **"B-1 (권고)"** — `push`를 통합·배포 브랜치로 좁힌다.

### A. 기준 판정을 스크립트 하나로 모았다

`scripts/ci_base_ref.py` 신설(보호 경로에 등록). 워크플로 YAML 안의 셸 분기는 시험할 수
없으므로 판정을 빼고 단위 시험 29칸을 붙였다(`tests/test_tk212_ci_base_ref.py`).

규칙은 이벤트를 보지 않는다.

1. HEAD가 병합 커밋이면(부모 2개 이상) **첫 부모**. `pull_request` 실행은 `refs/pull/<N>/merge`를
   꺼내므로 그 첫 부모가 **지금의** 기준 브랜치 끝이다. `base.sha`(PR 마지막 갱신 시점 값)보다
   정확하다 — 그 뒤 병합된 다른 PR의 효과가 이 PR 몫으로 섞이지 않는다(#120 문제도 함께 해소).
2. 통합·배포 브랜치 푸시면 직전 커밋.
3. 그 밖이면 통합 브랜치와의 공통 조상.
4. 어느 것도 풀리지 않으면 직전 커밋, 그마저 없으면 빈 트리.

위 '할 일' 3('`BASE`를 항상 PR base로 고정')은 이 규칙으로 **대체한다** — `base.sha`는 PR이
마지막으로 갱신된 시점의 값이어서 그 자체로 부정확하다.

`score-gate.yml`의 기준 설정 7곳(회귀·하드코딩·문구 대조·시험 삭제·보호 경로·버전 정책·은퇴
세트)을 전부 이 호출로 바꿨다. 두 워크플로에 `github.event` 기준 참조는 남지 않았다.

### B. 트리거를 좁혔다

`push: branches: ["**"]` → `[main, Steve_ACASiaLAW]`. 6차 독립 감사의 시정 조치를 되돌리는
것이므로 사용자 결정을 받았다. 감사가 지적한 '구현 브랜치 푸시에 점수 게이트만 돌아 기존
시험의 새 실패가 가려지는 것'은 `pull_request` 실행이 두 워크플로 전체를 돌리는 것으로 그대로
막힌다.
