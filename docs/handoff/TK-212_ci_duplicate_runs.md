# TK-212 PR 하나에 CI 실행이 둘 트리거되어 필수 확인 결론이 엇갈린다 (평가 측 CI 자산)

- 발견일: 2026-11-19 (평가 세션, #339·#341·#343 병합 과정)
- 종류: **평가 측 CI 자산 결함.** 제품 결함이 아니다
- 상태: open

## 증상

PR 하나의 같은 head SHA에 CI 워크플로 실행이 **둘** 걸린다. 한쪽이 취소되거나 다른 기준(base)으로
돌면서 같은 이름의 필수 확인이 서로 다른 결론을 낸다. GitHub 브랜치 규칙은 **더 늦게 끝난 결론**을
세므로, 성공 결론이 있어도 병합이 막히거나 반대로 실패가 가려질 수 있다.

실제로 세 번 막았다.

| PR | 증상 | 결과 |
|---|---|---|
| #339 | 같은 head에 실행 2개. `테스트 (SQLite + PostgreSQL/pgvector + Redis)` 집계 잡이 한쪽에서 `SQLite: cancelled / PostgreSQL: cancelled`를 받아 실패 보고 | 평가 측이 취소임을 가려냄 |
| #341 | `점수 하락 게이트`가 한 실행에서 success(22:57), 다른 실행에서 **cancelled**(23:07). 규칙이 늦은 쪽을 세어 **병합 거부**(`Required status check "점수 하락 게이트" is cancelled`) | 워크플로 재실행으로 해소 |
| #343 | `점수 하락 게이트`가 한 실행에서 success, 다른 실행에서 **failure**. 두 실행의 `BASE`가 달라 `check_test_edits.py`의 기준이 PR base(`556dac84`)와 직전 head(`1d27895f`)로 갈렸다 | 평가 측이 로그를 읽어 점수 하락이 아님을 확인 |

#343의 사례가 특히 나쁘다. **같은 커밋에 대해 게이트가 서로 다른 기준으로 돌아 결론이 갈린다.**
기준이 직전 head면 같은 PR 안의 시험 교체가 '기존 시험 삭제'로 잡힌다.

## 평가 측 확인 (정적)

- `.github/workflows/ci.yml`의 `BASE` 결정은 아래 꼴이다.

      BASE="${{ github.event.pull_request.base.sha }}"   # 또는 event.before
      if [ -z "$BASE" ] || [ "$BASE" = "0000...0" ] || ! git cat-file -e "$BASE^{commit}"; then BASE=HEAD~1; fi

  실행이 `pull_request`로 트리거될 때와 `push`로 트리거될 때 쓰는 값이 다르다. 두 트리거가 모두
  걸리면 같은 head에 기준이 다른 실행이 둘 생긴다.
- 취소는 뒤 커밋이 앞 실행을 밀어낼 때 생긴다. 취소된 필수 확인이 **성공 결론을 덮는다.**

주원인은 **미검증**이다. 트리거 조합(`push` + `pull_request`)과 `concurrency` 설정을 함께 보아야 한다.

## 할 일 (평가 측)

1. **진단.** 같은 head에 실행이 둘 생기는 트리거 조합을 워크플로 파일에서 확정한다. 추정으로
   하나를 고르지 않는다.
2. **중복 제거.** `concurrency` 그룹을 PR·브랜치 단위로 두고 `cancel-in-progress`를 쓰되,
   **필수 확인을 내는 잡이 취소 상태로 남지 않게** 한다. PR에서는 `pull_request`만, 브랜치
   직접 푸시에서는 `push`만 돌게 트리거를 가른다.
3. **기준 고정.** 게이트의 `BASE`를 **항상 PR base**(`github.event.pull_request.base.sha`)로
   고정한다. 직전 head를 기준으로 쓰면 같은 PR 안의 정당한 시험 교체가 삭제로 잡힌다.
   `push` 실행에서는 `merge-base`를 쓴다.
4. **확인.** 같은 PR에 커밋을 두 번 밀어 실행이 하나만 남고 필수 확인 결론이 하나인지 본다.

## 수용 기준

1. PR 하나의 head SHA에 CI 실행이 하나만 남는다
2. 필수 확인 이름마다 결론이 하나다(취소 결론이 성공을 덮지 않는다)
3. 게이트의 기준이 PR base로 고정되어 같은 PR 안의 시험 교체가 '기존 시험 삭제'로 잡히지 않는다
4. 기존 CI 단계와 필수 확인 이름은 바꾸지 않는다(브랜치 보호 규칙이 이름으로 걸려 있다)

## 미검증

주원인(트리거 조합·`concurrency`)을 아직 가리지 않았다. 증상은 세 PR에서 재현됐다.
