# 0.21.0 → 0.22.0 배포 후 온라인 비교·정리 절차

사용자 지시(2026-11-15): 0.22.0 릴리스 후 온라인 평가로 개선·미해소·추가 보완을 분석하고, 평가 후 사용한 시험 프로젝트를 삭제한다. 이 문서는 실행 계획이며 0.22.0의 실측 또는 수용 판정이 아니다. 배포 확인 → 평가 → 근거 보존 → 프로젝트 정리 → 비교 보고를 하나의 완료 절차로 삼는다.

## 1. 착수 및 조건 고정

1. 운영 `/api/health`에서 버전 0.22.0, 릴리스 커밋 전체 SHA, DB 정상 여부를 확인한다. GitHub 태그만으로 배포 완료로 보지 않는다. 실행 중 SHA가 바뀌면 묶음을 분리한다.
2. 실제 포함된 PR/TK를 대조하고 [기능별 평가표](FEATURE_ONLINE_EVALUATION.md)를 갱신한다. 병합·CI 통과와 운영 해소를 구분한다. 0.21.0의 봉인시험 대체 결정은 다른 버전으로 자동 확장하지 않는다.
3. 입력·정답지·명세 해시, 사건/실행/보안 설정, 모델 ID·라우팅·프롬프트·정책·추출기 판, 런타임, 공식 DB 기준일/상태, RAG 파일 리비전/스냅샷을 저장한다. 비밀값과 세션 쿠키는 저장하지 않는다.
4. 시험 전용 프로젝트를 새로 생성하고 생성 응답의 ID를 비공개 실행 장부에 즉시 적는다. 기존 사건 자료는 승인된 원본의 사본을 전용 프로젝트에 올려 시험한다. 이름·태그 검색만으로 삭제 대상을 추정하지 않는다.
5. 0.21.0 원본 보고서와 입력을 보존하고 같은 채점 명세로 비교한다. 모델·DB·Drive 변경이 있으면 영향과 비교 한계를 적는다. 구버전 재실행이 필요하면 격리 환경에서 수행하며 운영을 임의로 되돌리지 않는다. 후향 재채점은 새 온라인 실행과 구분한다.

## 3. 결과 정리와 추가 보완

결과 파일은 `online_compare_0210_0220_<실행일>.md/json`으로 작성한다. 항목마다 **0.21 근거 → 0.22 실측 → 조건 차이 → 판정 → 원인·해결안 → TK/담당/수용 기준**을 기록한다.

- 판정: `개선 확인`, `일부 개선`, `미해소`, `회귀`, `판정 보류`, `기존 통과 유지`, `신규 확인` 중 하나. 점수·성공률의 분모와 미실행 건수를 병기한다.
- TK 종결은 실제 운영 수용 기준을 충족한 근거가 있어야 한다. 사본 시험/CI/병합/배포/운영 재측정 단계를 따로 기록한다.
- 미해소·회귀는 같은 원인 TK에 재현 조건, 영향, 코드/외부 의존 원인, 수정 방안, 회귀 대조, 담당 및 다음 완료 기준을 연결한다. 원인 미확정은 추정과 확인 사실을 분리한다.
- 결과 요약은 `version_verdicts`에, 상세는 비교 보고서에, 구현 지시는 `NEXT_FOR_ANTIGRAVITY`와 TK에, 진행 상태는 `ticket_registry`에 반영한다. 누적 기록은 덧붙인다. 비공개 원문/프로젝트 ID/인증정보를 GitHub에 게시하지 않는다.

## 4. 평가 프로젝트 정리 — 모든 온라인 평가에 적용

실행 장부 양식: [online_project_cleanup_record.csv](online_project_cleanup_record.csv). 실제 ID가 채워진 장부는 저장소 밖 비공개 평가 폴더에 둔다.

1. **대상 등록:** 전용 프로젝트 생성 직후 `created_for_evaluation=true`, 생성 응답의 ID, 시험 ID, 문서/실행 ID를 기록한다. 기존 사용자 프로젝트는 `borrowed`로 표시하고 자동 삭제에서 제외한다. 기존 프로젝트를 사용한 과거 시험도 같은 원칙을 적용한다.
2. **종료 확인:** 모든 실행이 완료/부분완료/실패/취소 상태인지 확인한다. 대기·진행 중이면 완료 수집 또는 필요한 취소 후 종료 확인까지 정리를 보류한다. 평가 실패도 보고서/진단을 보존한 후 정리한다.
3. **근거 보존:** 입력과 명세/정답지 해시, 결과 JSON, 실행 manifest, 채점·오류·조건 기록을 비공개 위치에 저장하고 SHA-256 및 재열기/압축 무결성을 확인한다. 결과 묶음을 사용자에게 제공한다. 파생 점수만 남기고 원본 보고서를 지우지 않는다.
4. **삭제 전 대조:** 생성 장부의 정확한 ID, 프로젝트 이름/태그, 소속 문서·실행 목록을 API와 대조한다. 모르는 문서/실행이 추가되었거나 소유 관계가 불명확하면 그 프로젝트만 보류한다. 전체 계정 목록에 일괄 삭제를 적용하지 않는다.
5. **앱에서 삭제:** `DELETE /api/projects/{project_id}`로 휴지통 이동한다. 현재 API의 204가 성공이다. 409는 실행 중/충돌 등으로 기록하고 해결 전 완료로 표시하지 않는다. 응답이 끊기면 상태 조회로 확인한 후 재시도한다.
6. **사후 확인:** 일반 목록에서 사라지고 `GET /api/projects?deleted=true`의 해당 ID에 `deleted_at`이 있는지 확인한다. 삭제 시간·HTTP 결과·확인 결과를 장부에 기록한다. 휴지통 이동은 `TRASH_VERIFIED`, 보류는 사유와 후속 조치를 적는다.
7. **보존 범위 명시:** 이 절차의 기본 삭제는 앱의 휴지통 이동이며 서버 원본의 영구 파기가 아니다. `DELETE /api/projects/{id}/purge`는 호출하지 않는다. 영구 삭제를 별도로 지시받으면 보존 검증과 대상 대조 후 시행하고 DB/파일 삭제 오류까지 확인한다. Drive 공용 기준 자료와 기존 사건 프로젝트는 이 정리의 대상이 아니다.
8. **보고 완료:** 기능 판정과 정리 상태를 별도로 보고한다. 삭제 실패를 숨기지 않으며, 근거 보존 실패 시 삭제를 멈추고 `CLEANUP_BLOCKED`로 인계한다. 다음 평가에는 새 전용 프로젝트를 만든다.

향후 세션의 착수 문서로 이 계획을 사용한다. 별도의 예약 작업이나 릴리스 감시 자동화가 설치된 것은 아니다.
