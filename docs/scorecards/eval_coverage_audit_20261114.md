## 1. 결론
- **지금 체계는 '정답 항목을 맞혔는가'는 재지만 '파이프라인이 의도대로 돌았는가'는 재지 않는다.**
  - 실증: 0.18.0부터 법리 규칙 단계가 모든 문서에서 예외로 중단됐다(F1).
  - 그런데 CI·verify_all 전체(10,230건)·고정·은퇴 세트·온라인 case9(23/23 통과)가 모두 통과로 냈다.
- 공식 DB·모델·Drive의 실연동 점검 워크플로는 0.16.0 이후 모든 릴리스에서 건너뛰어졌다(F3).
- 탐지 유형 97개 가운데 35개는 채점기와 온라인 명세 어느 쪽으로도 재지 않는다(F4).
- 보완:
  - 평가 측 도구 5종을 더했다(4절).
  - 제품 결함 1건(TK-177)을 사본에서 사전 검증해 지시를 준비했다.
  - 운영 환경이 필요한 RAG 결함 1건(TK-178)은 조사 요청으로 올린다.
- 온라인 채점으로 **전환**하기보다 **두 층을 함께** 두는 것이 맞다(5절).
  - 오프라인은 회귀·하드코딩의 결정론 게이트로 남긴다.
  - 온라인은 실행 상태 점검과 '온라인 봉인 실행'으로 넓힌다.

## 3. 발견(실증)
- **F1. 법리 규칙 단계 NameError(0.18.0~0.21.0)**
  - 증상: 운영 실행 7건 모두에서 `run_manifest.engines.legal_rules.errors = ["doc_…: NameError"]`.
  - 오프라인 재현: 개발 문서 13건 중 12건에서 같은 오류. 화면 경고는 "법리 규칙 검토 경고: name 'os' is not defined"이다.
  - 원인: `packages/verification_engine/pipeline.py`가 `os`를 들여오지 않았다. 1055행 `os.environ.get("LV_ENABLE_CAUSE_OF_ACTION_REVIEW")`에서 NameError가 난다. 51a51ab(11-10, LV-06-R2)에서 들어왔다.
  - 영향:
    - 같은 블록 앞쪽의 `review_legal_rules`·`pleading_structure_findings` 결과는 이미 담긴 뒤라 점수는 같았다.
    - 그러나 단계가 오류 상태로 기록되고, 사용자 화면에 코드 오류 문구가 경고로 나간다.
    - 요건사실 점검(플래그 켬)은 켜도 돌 수 없었다.
  - 놓친 이유: 단계가 예외를 삼키고(`stage.error`), 어느 시험·게이트도 엔진 오류 수를 보지 않았다.
  - → **TK-177**(제품, 사본 사전 검증 완료), 게이트 보완 S1·S2·S3.
- **F2. Drive 참고자료 동기화가 매번 미완료, 판례표 격리**
  - 운영 실행 7건 모두 `reference_library.status = PARTIAL`, `reference_sync` 오류 '참고자료 전체 동기화·읽기를 완료하지 못함'.
  - 0.19.0 case9: 35개 중 23개 색인. 문제 건수는 격리 5·암호 1·부분 읽기 10·지시문 쪽 제외 6이다.
  - 판례표 후보(xlsx, 발견 행 3,556)가 `REFERENCE_QUARANTINED`로 **색인 0행**이다. RAG의 정형 판례 조회 원천이 빠진 채 돈다.
  - case9 RAG-1·2는 다른 참고자료로 통과해 드러나지 않았다.
  - 격리 사유가 실제 위험인지 오판인지는 운영 Drive 파일로만 확인할 수 있다.
  - → **TK-178**(조사 요청, 사용자 환경 `python -m scripts.check_drive_references` 실행 필요).
- **F3. 실연동 워크플로가 릴리스마다 건너뜀**
  - `live-source-check`·`live-integration`·`official-sources`는 workflow_dispatch 또는 커밋 메시지 표지(`[live-integration]` 등)가 있어야 돈다.
  - 0.16.0~0.20.0 main 병합 실행이 모두 skipped였다.
  - `docs/live_integration_results.json`의 마지막 기록은 2026-09-25(e1c780c)다.
- **F4. 측정 공백 유형**
  - 탐지 유형 97개 중 채점기가 점수를 줄 수 있는 것은 62개, 온라인 명세가 지정한 것은 19개다. 둘 다 아닌 것이 35개다.
  - 그중 16개는 제품 코드가 실제로 내는데 시험 코드·명세 어디에도 이름이 없다: 서명·메타데이터·위치정보 노출, 숨김 시트, 지문, 추적 표지, 수사 신호 등.
  - 표: `eval_coverage_20261114.json`(도구 S4).
- **F5. 봉인 채점의 사각**
  - 봉인 성적표에 결함 유형별 항목 수가 없어, 봉인 세트가 어느 유형을 덮는지 사용자도 알 수 없었다(S1로 보완).
  - 봉인 채점기는 개인정보 마스킹을 채점하지 않는다.
- **F6. 온라인 명세는 정답 항목만 본다**
  - 같은 실행에서 엔진 오류·동기화 미완료가 있어도 23/23이 나왔다(S3으로 보완).
- 참고: 0.19.0 탐침 B의 모델 호출 70건 중 3건 실패(형식 오류 2, 출력 한도 잘림 1, 4%). 기준(10%) 안이지만 실행 상태 표에 남는다.

## 5. 오프라인 대 온라인 — 전환이 아니라 두 층
| | 오프라인(고정·은퇴·봉인·CI) | 온라인(배포 서비스) |
|---|---|---|
| 재현성 | 같은 입력이면 같은 출력. 항목 단위 회귀를 PR마다 막을 수 있다 | 모델 응답이 실행마다 다르다(case9 AI 판별 점수 0.38~0.68, TK-161). DB·Drive 상태도 바뀐다 |
| 비용·속도 | 무료, PR마다 수 분 | 모델 과금, 문서당 수 분(case9 약 5분), 사용자 실행 필요 |
| 재는 것 | 탐지·채점·개인정보·인젝션·파서 | 공식 DB·모델·Drive·AI 판별·배포 정상 동작 |
| 하드코딩 감시 | 정답 문구·사건 값 대조 게이트 가능 | 감시 수단 아님 |

- 오프라인을 빼면 PR마다 도는 결정론 회귀·하드코딩 게이트가 없어진다. 그러면 '같은 코드인데 점수가 다름'과 '코드가 나빠짐'을 구분할 수 없다.
- 반대로 온라인을 지금처럼 case9 1건과 탐침 몇 건의 정답 항목에만 두면 F1~F3을 못 잡는다.
- 제안(사용자 결정 필요):
  - **U1. 온라인 봉인 실행(릴리스마다 1회)**
    - 봉인 세트를 배포 서비스(또는 키를 넣은 CI 러너)로 돌린다.
    - 채점기의 `db_available=True` 모드로 공식 DB 항목(CIT-NX-DB·SRC-UNV 등)까지 채점한다. 채점기는 이미 이 모드를 지원한다.
    - 봉인 문서가 마스킹을 거쳐 외부 모델에 보내진다는 점과 비용을 사용자가 정한다.
  - **U2. 실연동 점검을 릴리스 절차에 넣는다**
    - 릴리스 PR 병합 커밋에 `[live-integration] [live-check]` 표지를 넣거나 병합 직후 workflow_dispatch를 1회 실행한다.
    - 결과를 판정서에 적는다.
    - 실연동 시험에 법령 연혁·자치법규·별표·전합 역조회를 더한다(구현 측 티켓).
  - **U3. RAG 대조군**
    - Drive에 음성 대조 자료(주장과 무관한 자료)와 지지 자료를 두고, case9 명세에 `no_rag_relationship`·지지 관계 항목을 더한다.
    - TK-178로 판례표 격리 원인을 먼저 확인한다.
  - **U4. 봉인 출제 사양**(Codex 격리 세션 전달)
    - 채점기 결함 유형 30종 각 1건 이상, 대조군·오탐 함정을 넣는다.
    - F4의 미측정 유형 중 오프라인으로 만들 수 있는 것(메타데이터·숨김 시트·서명·추적 표지)을 넣는다.
    - 개인정보 정답(종류·위치)을 넣는다. 채점기 확장은 평가 측이 맡는다.
  - **U5. AI 작성 판별 반복 측정**: 릴리스마다 case9 3회 실행을 표준 절차로 한다(TK-161 방식).
