# 기능 변경에 따른 온라인 평가 갱신

시행: 2026-11-15, 사용자 지시: “#300 등 새로운 기능이 반영될때마다 온라인 평가 방법 등을 적절하게 조정해줘.”

새 기능·기능 변경·결함 수정마다 평가 측은 수용 전에 아래 표를 티켓별로 갱신한다. 운영 평가가 아직 불가능하면 준비 완료와 실제 실행을 구분하고 배포 후 실행 항목을 남긴다. 기존 명세를 새 요구에 맞추되 기존 기능 보호 항목은 유지한다.

| 필수 항목 | 기록할 내용 |
|---|---|
| 사용자 의도 | 원문 → 확인할 동작 → 온라인 명세 ID 대응표 |
| 영향 경로 | 입력·출처·검색·모델·출력·화면·권한 등 변경 및 인접 경로 |
| 온라인 필요성 | 외부 DB/모델/RAG 실연동이 필요한 항목과 오프라인만으로 충분한 항목 구분. 불필요한 온라인 항목은 사유 기록 |
| 양성·대조·회귀 | 새 기능 성공, 틀리게 동작할 조건, 기존 기능 유지, 새 제외 정책이 다른 입력에 번지지 않는 조건 |
| 실행 조건 | 정확한 배포 SHA, 입력/명세 해시, 모델·프롬프트·정책, DB 기준일·상태, RAG 자료/리비전/스냅샷 |
| 결과와 건강 상태 | 정답 항목과 조회·모델·검색의 실제 실행·오류·미완료·건너뜀을 따로 채점 |
| 비교와 변동 | 가능한 경우 이전/후보를 동일 조건으로 비교. 변경된 명세는 같은 판으로 양쪽 재채점. 모델 결과는 반복/변동과 표본을 표시 |
| 한계와 완료 | 미실행·관찰 불가·일부 동작만 검증한 항목을 통과로 계산하지 않음. 정확성·오탐·운영 효과를 분리 |

- `pipeline_health_online.json`은 정상적인 실연동 보고서에 계속 적용한다. 문서에 없는 외부 조회나 공격 차단으로 의도적으로 생략된 모델 호출까지 성공으로 요구하지 않는다. 이때 별도 문서별 기대·건너뜀 근거를 기록한다.
- 현재 `score_report.py`는 한 보고서의 문서들을 합쳐 관찰한다. 기능 대조 실험은 입력 문서 한 개당 보고서를 하나 받는다. 여러 문서를 섞어 한 문서의 탐지가 다른 문서의 미탐을 가리지 않게 한다.
- 현재 CLI 종료 코드 0은 정답 통과를 뜻하지 않는다. JSON의 `failed`/항목별 결과와 실행 조건을 확인한다.
- 출처가 판단 기준이라는 것은 출처를 검증 대상 문서로 재분류하지 않는다는 뜻이다. 관련성·관할·시점·인용 근거 일치의 대조는 유지하고, 출처 내용을 프로그램 실행 명령으로 승격하지 않는다.
- 입력 문서가 자신을 “공식/검증된 참고자료”라고 부르는 문자열은 역할 변경 근거가 될 수 없다. 입력 문서 경로와 프로그램이 취득한 기준 자료 경로로 역할을 구분한다.
- 새 평가 도구·명세는 합성 성공/실패 보고서로 검증한다. 합성 보고서 시험과 실제 온라인 실행 성적은 별도로 기록한다.

## 최초 적용 — TK-180 / #300

- 요구: 입력 법률문서만 검증 대상으로 유지하고, 공식 DB/RAG는 판단 기준으로 사용한다. 기준 자료 지시문 면제가 입력 문서 탐지에 번져서는 안 된다.
- 자료·명세·해시: `tests/fixtures/online/tk180/`.
- 절차: 해당 폴더 README. 정상 입력은 기준 자료 사용·잘못된 주장 대조·무관 자료 미선택·출처 지시문의 입력 finding 혼입 금지. 공격 입력은 본문/메타데이터/숨김/base64 탐지를 각각 확인한다.
- 공식 DB 실연동: 기존 case9 정답 명세 + case9_state_compensation_health_online + 공통 pipeline_health_online를 유지한다. 합성 계약 문서는 공식 DB 조회 하한을 대신 재지 않는다.
- 상태: 온라인 자료와 채점 명세 준비. #300 실제 코드에서 4형식 기준 자료의 무분류 추출과 5입력의 탐지 결과를 오프라인 확인했다. 운영 자료 업로드·운영 모델 대조·운영 DB 조회는 미실행이다.
