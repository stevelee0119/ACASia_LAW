# 프로그램 버전 정책 (변경 분류 기준 버전 관리)

시행: 2026-10-02 · **개정: 2026-10-24(사용자 채택 — 평가 측 제안 '변경 분류 기준 + 오류 감소율')** · 점검 도구: `scripts/check_version_policy.py`
대상: `packages/common/config.py`의 `Settings.version`(X.Y.Z), `docs/releases.json`, README 변경표. `rule`·`prompt` 버전은 이 정책의 대상이 아니다.

근거:
- Semantic Versioning 2.0.0(https://semver.org/): 자리는 변경의 종류(호환되지 않는 변경 / 호환되는 새 기능 / 잘못된 동작 수정)를 나타낸다. "If your software is being used in production, it should probably already be 1.0.0."(FAQ)
- Keep a Changelog 1.1.0(https://keepachangelog.com/en/1.1.0/): 변경 분류 Added·Changed·Deprecated·Removed·Fixed·Security.

## 1. 한 줄 원칙
**버전 자리는 커밋 수나 점수 크기가 아니라, 그 릴리스에서 평가 측이 수용한 변경 가운데 가장 높은 분류로 정한다.** 성능은 오류 감소율(RER)로 재어 분류의 근거와 릴리스 노트의 지표로 쓴다. 점수 하나만으로 정수(X)를 올리지 않는다.

## 2. 자리의 뜻
| 자리 | 표기 | 뜻 |
|---|---|---|
| 정수 X | X.0.0 | 호환되지 않는 변경 또는 안정성 이정표(1.0.0 등). **사용자 승인 필수** |
| 소수점 첫째 자리 Y | X.Y.0 | 새 기능·사용자에게 보이는 기능 변경·큰 성능 개선 |
| 소수점 둘째 자리 Z | X.Y.Z | 결함 수정·보안 수정·작은 성능 개선 |
- 올린 자리 아래 자리는 0으로 되돌린다(0.13.1 → 0.13.2 / 0.14.0 / 1.0.0). 한 번에 한 단계만 올린다. 내려가기·건너뛰기는 하지 않는다.
- 버전은 **릴리스 단위로만** 올린다. 구현 작업 커밋은 버전을 바꾸지 않는다.

## 3. 성능 지표 — 오류 감소율(RER)
- **RER = (후보 점수 − 직전 릴리스 점수) ÷ (100 − 직전 릴리스 점수).** 남은 오류 가운데 없앤 비율이다. 점수가 높아져도 같은 의미를 유지한다(천장 효과 보정).
  - 판정용 값은 고정 dev·holdout **합산 RER**(두 세트 득점 합 기준)로 하고, 세트별 RER을 함께 적는다.
  - 예: holdout 80.1→81.9는 +1.8점, RER 9.0%.
- 상승분은 **탐지 개선분만** 센다(표시 보강 제외). 같은 유형 항목이 은퇴·train에서도 확인되어야 한다(평가 세트 문구 일치로 오른 것 제외, 전달문 2-2절).
- 측정 주체는 평가 측이고, 직전 릴리스와 후보를 **같은 조건**(오프라인 `LV_ALLOW_NETWORK=0`, Linux, python 3.11, 한국어 OCR, 같은 채점기·세트)에서 함께 잰다. 기록된 숫자끼리 비교하지 않는다. 평가 세트가 바뀌면 두 쪽을 새 세트로 다시 잰다.
- 측정하지 못한 것(AI 작성 판별·공식 DB 대조·Drive 대조 등 온라인 영역)은 판정서에 "측정 못 함"으로 적는다.

## 4. 상향 전제 (모두 충족해야 어떤 자리든 올릴 수 있다)
- P1 회귀 게이트 종료 0(`scripts/regression_gate.py`), P2 고정·은퇴 항목 회귀 0·오탐·A등급 증가 0, P3 하드코딩 금지 규약(전달문 2-2절) 위반 0, P4 전체 시험 통과(사용자 결정 대기 시험 제외), P5 열린 신규 회귀 티켓 0, P6 평가 측 판정서 작성.

## 5. 분류 기준 (2026-10-24 사용자 채택)
판정서의 `basis`에 해당 분류를 모두 적는다. 자리는 그 가운데 **가장 높은 것**이다.
| 자리 | `basis` 값 | 인정 조건(평가 측 판정) |
|---|---|---|
| X (major) | `breaking` | 호환되지 않는 변경: 공개 API·보고서 형식·DB 이전 등 사용자 조치가 필요한 변경 |
| X (major) | `milestone` | 안정성 이정표(1.0.0). 아래 5.1 조건 충족 |
| Y (minor) | `added` | 새 탐지 유형·새 기능. 실제 진입점 시험으로 동작 확인 |
| Y (minor) | `changed` | 사용자에게 보이는 기능·편의성 변경. '전 요구 → 새 확인 위치' 대응표, 화면 시험, 사용자 확인 |
| Y (minor) | `deprecated` · `removed` | 기능 폐기 예고 또는 화면 기능 제거(공개 API 제거는 `breaking`) |
| Y (minor) | `performance_minor` | 합산 RER **10% 이상**, 각 세트 하락 없음, 은퇴·train 같은 유형 동반 확인. 판정서에 `rer` 수치 |
| Z (patch) | `fixed` | 오탐·A등급 오탐·실패·운영 결함 감소(측정 근거) |
| Z (patch) | `security` | 보안·개인정보 수정 |
| Z (patch) | `performance_patch` | 합산 RER 0 초과 10% 미만의 순증(탐지 개선분) |
| Z (patch) | `known_open` | 보호 시험의 알려진 미해결(strict xfail·KNOWN_OPEN) 해소 |
- **상향 없음:** 리팩터·문서·시험 추가·평가 도구만 바뀐 경우, 회귀 복구로 직전 수준으로만 돌아온 경우. 판정 결과와 근거를 HISTORY에 남긴다.
- **정성 요소는 점수로 매기지 않는다.** 기능·편의성은 `added`·`changed`로 분류하고 검증 근거(진입점 시험·대응표·사용자 확인)로만 인정한다(주관 점수는 재현이 안 되고 점수 맞추기 동기를 만든다).
- RER 10%는 평가 측 제안값이다(표준값 없음). 첫 판정 뒤 실측과 함께 다시 검토한다.

## 5.1 1.0.0 이정표 (사용자 승인)
SemVer는 운영 중인 소프트웨어는 1.0.0 이상을 권한다. 다음을 모두 충족하면 평가 측이 1.0.0 판정서(`basis: ["milestone"]`, `user_approved: true`)를 올리고 사용자가 정한다.
1. 공개 인터페이스(REST API, 보고서 형식)를 문서로 정하고 이후 호환되지 않는 변경은 X 상향으로만 한다고 확정.
2. 새 봉인 세트로 직전 릴리스와 같은 조건 측정을 마침.
3. 연속 2회 릴리스에서 P1 회귀 0.

## 5.2 배포와의 관계(2026-10-04 사용자 결정)
- 버전 상향은 배포 조건이 아니다. 배포(`main` 병합)는 [RELEASE_PROCEDURE](RELEASE_PROCEDURE.md) 2절 조건으로만 하고, 이 정책의 상향 요건을 채우지 못하면 버전을 유지한 채 배포한다.
- 상향 판정이 나면 판정서와 버전 커밋이 `Steve_ACASiaLAW`에 들어간 뒤 릴리스 PR을 연다.

## 6. 절차
1. **구현:** 작업 커밋에서 `version`·`docs/releases.json`·README 변경표를 건드리지 않는다.
2. **평가:** 릴리스 후보에서 같은 조건으로 측정하고, 상향 요건을 채우면 `docs/scorecards/version_verdicts.json`에 **판정서**를 추가한다(`version`·`from`·`level`(major|minor|patch)·`measured_commit`·`conditions`·`evidence`(수치)·`decided_by`·`decided_at`, **2026-10-24 이후 판정서는 `basis`(5절 분류 목록)와 `performance_minor`일 때 `rer`**, 정수는 `user_approved: true`). 근거는 HISTORY에도 적는다.
3. **구현:** 판정서가 들어 있는 브랜치에서 **버전 커밋 1개**를 만든다. 바꾸는 것은 `packages/common/config.py`의 `version`, `docs/releases.json` 항목(변경 내용에 판정서의 근거 수치와 포함 티켓), `python scripts/update_readme.py`가 갱신하는 README 표뿐이다. 다른 변경을 섞지 않는다.
4. **평가:** `python scripts/check_version_policy.py --base <기준 커밋>`이 통과하는지 확인한다(`점수 게이트` 워크플로에도 들어 있다). 판정서 없는 상향, 등급·자리 불일치, 건너뛰기, 같은 판정서 재사용은 실패다.
5. **사용자:** 정수 상향(1.0.0 포함)과 분류 기준·RER 임계값 변경을 승인한다. 기준선(`baseline.json`) 갱신은 별개로 사용자 승인이 필요하고, 갱신하면 그 시점의 프로그램 버전을 `baseline.json`에 적는다.

## 7. 경과 조치
- 2026-10-24 개정 전 판정서(0.10.0~0.13.1)는 옛 기준(점수 임계값)으로 판정된 그대로 둔다. 점검 도구는 `decided_at`이 2026-10-24 이후인 판정서에만 `basis` 규칙을 적용한다.
- 0.9.13 이전의 이력(커밋마다 올린 0.9.x)은 소급해 바꾸지 않는다.
- 0.9.13 이후 네 라운드가 버전 변경 없이 쌓여 있다. 첫 판정은 5차 구현 검증 뒤에 한다(4차 상태는 열린 신규 회귀 TK-29가 있어 P5를 채우지 못한다).
- 점검은 푸시된 범위의 모든 커밋을 본다. 이 정책을 시행한 커밋 이후의 상향에만 적용한다.
