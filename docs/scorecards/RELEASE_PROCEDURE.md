## 0. 전제(사용자 확인 2026-10-04)
- 배포 브랜치는 `main`이다. Render는 `main`에 푸시(병합)되면 **자동으로 재배포**한다. 따라서 **`main` 병합이 곧 배포**이며, 병합이 마지막 승인 단계다.
- `main`에는 ruleset 24413473이 걸려 있다: 필수 확인 3개(점수 하락 게이트·테스트·Docker OCR readiness), 강제 푸시 금지, 삭제 금지, 예외 없음.
- 통합 브랜치는 `Steve_ACASiaLAW`다(ruleset 24418330). 릴리스는 `Steve_ACASiaLAW` → `main` PR로만 한다.

## 1. 배포와 버전 상향의 분리
- **배포 조건과 버전 상향 조건은 서로 독립이다.**
  - 배포는 2절의 조건(평가 통과·봉인 시험·사용자 승인)만으로 한다.
  - 버전은 [VERSION_POLICY](VERSION_POLICY.md)대로 같은 조건에서 잰 성능으로만 정한다. 상향 요건을 채우지 못하면 버전을 유지한 채 배포한다.
- **분리 사유:**
  - 고정 시험 점수는 09-30 이후 81.7/79.2로 같다. 이 시험은 개인정보 경계 같은 수정 대상을 재지 않는다([HISTORY](HISTORY.md) 3절).
  - 버전 상향을 배포 조건으로 묶으면, 유출을 막은 수정 같은 안전 수정을 배포할 수 없다.
- 버전 판정이 상향이면, 그 판정서와 구현 측 버전 커밋 1개가 `Steve_ACASiaLAW`에 들어간 **뒤에** 릴리스 PR을 연다. 판정이 '상향 없음'이어도 판정 결과는 HISTORY에 남긴다.
- 성적표에 개인정보 지표를 넣어 버전 판정에 반영하는 일은 별도 과제다([process_review](process_review_2026-10-03.md) 6절 B-5).

## 2. 릴리스 조건(모두 충족)
1. **평가 판정 '통과':** [판정서](f1_gate_verdict.md)에 라운드 수용이 기록되어 있다(`verify_all` 종료 0, 비공개 세트 수용 기준 충족, 같은 SHA CI 필수 확인 3개 성공).
2. **봉인 시험:** 사용자가 `python scripts/scorecard.py --sealed-dir <경로>`로 실행하고, 점수가 기준선 아래로 내려가지 않았다(AGENT_ROLES 3절).
   - **적용 범위(2026-10-09 사용자 결정, 변경 범위 기준):** 직전 릴리스(`main`) 대비 **오프라인 탐지·채점·개인정보 엔진**을 바꾼 릴리스에만 봉인 시험을 한다. 그 밖(RAG·모델 호출 경로, 화면·API, 문서·시험만 바뀐 릴리스)은 오프라인 봉인 채점이 그 변경을 재지 못하므로 생략하고, 릴리스 PR에 '봉인 생략(변경 범위 밖)'과 근거(바뀐 제품 파일 목록)를 적는다. 버전 상향 여부는 이 판단에 쓰지 않는다.
   - 생략한 릴리스도 1·3·4 조건과 배포 직후 온라인 점검(4절)은 그대로 한다. 판단이 애매하면 봉인 시험을 한다.
2-1. **고정 비공개 벤치마크(2026-10-10 도입, 참고 지표):** 같은 세트로 운영본·후보를 `scripts/fixed_benchmark.py --record`로 재어 기록한다([FIXED_BENCHMARK](FIXED_BENCHMARK.md)). 후보가 운영본보다 낮으면 릴리스 PR 본문에 사유를 적고 사용자가 정한다. 세트가 아직 없으면 '미측정'으로 적는다.
2-2. **티켓 지표 갱신:** `python scripts/ticket_metrics.py`로 [TICKET_METRICS](TICKET_METRICS.md)를 갱신하고, 릴리스 후보의 상태는 `merged`로 유지한다. 실제 배포 완료·health SHA 확인 뒤에만 릴리스에 든 티켓의 `ticket_registry.json` 상태를 `deployed`(배포일 `deployed_on`)로 바꾼다.
3. **열린 P1 회귀 티켓 0:** 릴리스 대상 SHA에서 확인된 새 P1 회귀가 없다(알려진 미해결은 strict xfail·티켓으로 명시되어 있을 것).
4. **사용자 승인:** 릴리스 PR 병합은 사용자가 한다.

## 2-2. 릴리스 기준과 수용 조건 (2026-10-18 사용자 결정)
- **기준선:** 이번 릴리스가 수용되면 기준선(`baseline.json`)을 dev 82.6 / holdout 80.1로 올린다. 그다음 릴리스부터는 고정 dev·holdout 종합점수가 **기준선을 넘어야** 릴리스한다.
  - 넘었는지는 탐지 개선으로만 센다. 표시 보강(발췌·문맥 덧붙임으로 채점 토큰이 맞게 된 것)은 따로 적고 기준선 초과 근거에서 뺀다.
  - **예외:** 점수가 같더라도 ① 새 기능이 추가됐거나 ② 기존 오류(오탐·A등급 오탐·실패·운영 결함)가 줄었음을 평가 측이 측정으로 보이고 사용자가 인정하면 릴리스할 수 있다. 어느 경우에도 고정·은퇴 세트 회귀와 오탐 증가는 허용하지 않는다.
- **PR 수용 조건(세 갈래):** 다음 중 하나 이상을 입증하고, 회귀 0·하드코딩 0을 지킨다.
  - (가) 기존 점수 상승 — 같은 유형 항목이 train뿐 아니라 은퇴·고정 세트에서도 오른다(평가 세트 문구 일치로 오른 것은 제외).
  - (나) 새 기능 — 실제 진입점 시험으로 동작을 보인다.
  - (다) 사용자 지시 사항 개선 — 지시와 증거를 대응시킨다.
- **회귀·하드코딩 장치:**
  - CI: 점수 하락 게이트, 은퇴 세트 비교, 회귀 원장, 시험 삭제·약화 점검, 보호 경로, **평가 세트 문구 대조**(`check_train_phrase_overlap.py --eval-sets`, 은퇴·고정 세트 정답지와 대조, 일반 표현은 평가 측이 `approved_eval_phrases.json`에 올림).
  - 평가 측: train 원문 대조(train은 저장소 밖), 비공개 탐침, 일반화 확인.
  - 구현 측: PR 전에 `python scripts/precheck_pr.py --tests <바꾼 기능의 시험>`(점수 게이트·은퇴 비교·핵심 시험·평가 세트 문구 대조를 한 번에).
- **평가 자산 주기적 교체:** 릴리스 주기마다 평가 측이 교체 필요를 점검하고 사용자 승인으로 진행한다.
  - 개발 말뭉치(train/check)와 고정 벤치는 저장소를 연결하지 않은 Codex 격리 세션이 새로 출제한다.
  - 비공개 탐침 문장은 평가 측이 저장소 밖에서 새로 만든다. 판정 코멘트에 적은 탐침은 공개된 것으로 보고 다음 주기에 쓰지 않는다.
  - 은퇴 세트는 일반화 확인용으로만 쓰고, 릴리스 판정에는 새 봉인 세트를 쓴다(이번 릴리스만 봉인 생략, 사용자 결정 10-17).

## 2-5. 릴리스 기준 개정 — 게이트 + 가치 (2026-10-24 사용자 채택, 2-2·2-4의 '점수가 반드시 올라야 함'을 대체)
- 개정 사유: 점수 상승을 배포 필수 조건으로 두면 점수에 잡히지 않는 가치(화면·편의성 개선, 새 기능, 보안·개인정보 수정)를 배포할 수 없다. 예: 10-21 Steve 병합 D-1~D-4·TK-94가 0.13.1 뒤 배포되지 못함. 품질 하한은 아래 게이트(회귀 금지)로 지킨다.
- **게이트(모두 필수, 2-4의 2~4와 같음):**
  1. 고정 dev·holdout 각각 현재 릴리스 이상(같은 조건 동시 측정), 은퇴 4세트 각각 이상·항목 단위 회귀 0.
  2. 오탐 0·A등급 오탐 0·인젝션 방어 유지.
  3. `verify_all` 전체 모드 종료 0, 필수 CI 성공, 열린 P1 회귀 0, 배포 뒤 온라인 점검(4절).
  4. 사용자 승인(병합).
- **가치(하나 이상, 평가 측이 측정으로 보임):**
  - 점수 순증: 고정 두 세트 득점 합이 현재 릴리스보다 높음(크기 무관, 탐지 개선분만). 합산 RER을 적는다.
  - 새 기능(Added)·사용자에게 보이는 기능 변경(Changed): 진입점 시험·대응표·사용자 확인.
  - 측정된 결함 감소(Fixed): 오탐·A등급 오탐·실패·운영 결함.
  - 보안·개인정보 수정(Security).
- **긴급 패치 경로:** 보안·개인정보 유출·P1 회귀 수정은 가치 조건 없이 게이트만 통과하면 PATCH로 배포한다(봉인 시험 적용 범위는 2절 2를 따른다).
- **릴리스 노트:** `docs/releases.json`과 릴리스 PR 본문에 Keep a Changelog 분류(Added·Changed·Deprecated·Removed·Fixed·Security)별 변경, 고정·은퇴 점수와 세트별·합산 RER, 측정 조건, 측정 못 한 항목을 적는다.
- 버전 자리는 [VERSION_POLICY](VERSION_POLICY.md) 5절(변경 분류 기준)로 정한다. 버전과 배포는 계속 분리한다(1절).

## 2-6. 직전 릴리스 결함 교정 배포 — 간소 경로 (2026-10-25 사용자 지시)
사용자 원문: "TK-126~128은 오류를 교정한 것이니 바로 배포를 진행하는 것이 좋을 것 같아. 앞으로도 직전 릴리스의 사소한 오류를 수정한 것은 배포 절차를 간소화할 필요가 있어."
- **적용 대상:** 직전 운영 릴리스 뒤 Steve에 들어간 제품 변경이 모두 ① 직전 릴리스의 결함 교정(사용자 요구 미이행·표시 결함·회귀) 또는 ② 보안·개인정보 수정이고, 각 PR이 평가 측 수용(사용자 요구 PR은 사용자 화면 확인 포함)을 받은 경우. 결함 교정에 딸려 사용자가 화면으로 확정한 보완(같은 티켓 범위의 화면·기능)은 포함한다. 그 밖의 탐지 개선·새 탐지 유형이 섞이면 일반 경로(2·2-5절).
- **생략·대체:**
  1. 봉인 시험 생략. 단 탐지·채점·개인정보 엔진을 바꿨으면 평가 측이 **동등성 근거**(고치기 전후 엔진 출력 비교에서 차이 0 또는 의도된 차이만 + 고정·은퇴 점수 불변)를 판정서에 적는다. 근거를 못 보이면 일반 경로.
  2. 릴리스 후보의 `verify_all` 전체 모드 1회는, PR 수용 때 평가 측이 수용 SHA에서 돈 단계(scorecard·score_gate·regression_gate·hardcoding_diff·check_test_edits·check_protected_paths·check_version_policy·관련 시험)와 같은 SHA의 CI로 갈음한다. 릴리스 후보와 수용 SHA의 제품 diff가 0이어야 한다(버전 커밋·문서만 추가).
  3. 고정 비공개 벤치마크(2-1) 생략.
  4. 판정서는 짧게: 수용 SHA·포함 PR·분류(`basis`)·점수 불변·동등성 근거.
  5. 배포 직후 온라인 점검(4절)은 `/api/health`의 SHA·버전 확인으로 갈음한다. 온라인 경로(모델 호출·공식 DB·Drive)를 바꾼 경우에만 4절 전체를 한다.
- **유지(생략 불가):** 필수 CI 성공, 열린 P1 회귀 0, 기준선 이상(오탐 0·A 0·인젝션 방어), 버전 판정(VERSION_POLICY 5절 분류 그대로 — 간소 경로라고 자리를 낮추지 않는다), 사용자 병합 승인, 기록(HISTORY·DAILY_TREND·티켓 `deployed`).
- **순서:** ① 평가 PR(판정서·기록) Steve 병합 → ② 구현 측 버전 커밋(VERSION_POLICY 6절 3, CI·`check_version_policy`만으로 수용) → ③ 릴리스 PR(Steve → main, 본문은 판정서 요약) → ④ 사용자 병합 → ⑤ health 확인·기록.
- **첫 적용:** 0.15.0(TK-126·127 1단계·128·개인정보 정규식 ReDoS, #183 수용 SHA `2f61f82`).
