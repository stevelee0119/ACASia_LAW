## 1. 배포와 버전 상향의 분리
- **배포 조건과 버전 상향 조건은 서로 독립이다.**

- **분리 사유:**
  - 고정 시험 점수는 09-30 이후 81.7/79.2로 같다. 이 시험은 개인정보 경계 같은 수정 대상을 재지 않는다([HISTORY](HISTORY.md) 3절).
  - 버전 상향을 배포 조건으로 묶으면, 유출을 막은 수정 같은 안전 수정을 배포할 수 없다.

- 성적표에 개인정보 지표를 넣어 버전 판정에 반영하는 일은 별도 과제다([process_review](process_review_2026-10-03.md) 6절 B-5).

## 2-2. 릴리스 기준과 수용 조건 (2026-10-18 사용자 결정)
- **기준선:** 이번 릴리스가 수용되면 기준선(`baseline.json`)을 dev 82.6 / holdout 80.1로 올린다. 그다음 릴리스부터는 고정 dev·holdout 종합점수가 **기준선을 넘어야** 릴리스한다.
  - 넘었는지는 탐지 개선으로만 센다. 표시 보강(발췌·문맥 덧붙임으로 채점 토큰이 맞게 된 것)은 따로 적고 기준선 초과 근거에서 뺀다.
  - **예외:** 점수가 같더라도 ① 새 기능이 추가됐거나 ② 기존 오류(오탐·A등급 오탐·실패·운영 결함)가 줄었음을 평가 측이 측정으로 보이고 사용자가 인정하면 릴리스할 수 있다. 어느 경우에도 고정·은퇴 세트 회귀와 오탐 증가는 허용하지 않는다.
- **PR 수용 조건(세 갈래):** 다음 중 하나 이상을 입증하고, 회귀 0·하드코딩 0을 지킨다.
  - (가) 기존 점수 상승 — 같은 유형 항목이 train뿐 아니라 은퇴·고정 세트에서도 오른다(평가 세트 문구 일치로 오른 것은 제외).
  - (나) 새 기능 — 실제 진입점 시험으로 동작을 보인다.
  - (다) 사용자 지시 사항 개선 — 지시와 증거를 대응시킨다.
- **회귀·하드코딩 장치:**
  - CI: 점수 하락 게이트, 은퇴 세트 비교, 회귀 원장, 시험 삭제·약화 점검, 보호 경로, **평가 세트 문구 대조**(`check_train_phrase_overlap.py --eval-sets`, 은퇴·고정 세트 정답지와 대조, 일반 표현은 평가 측이 `approved_eval_phrases.json`에 올림).
  - 평가 측: train 원문 대조(train은 저장소 밖), 비공개 탐침, 일반화 확인.
  - 구현 측: PR 전에 `python scripts/precheck_pr.py --tests <바꾼 기능의 시험>`(점수 게이트·은퇴 비교·핵심 시험·평가 세트 문구 대조를 한 번에).
- **평가 자산 주기적 교체:** 릴리스 주기마다 평가 측이 교체 필요를 점검하고 사용자 승인으로 진행한다.
  - 개발 말뭉치(train/check)와 고정 벤치는 저장소를 연결하지 않은 Codex 격리 세션이 새로 출제한다.
  - 비공개 탐침 문장은 평가 측이 저장소 밖에서 새로 만든다. 판정 코멘트에 적은 탐침은 공개된 것으로 보고 다음 주기에 쓰지 않는다.
  - 은퇴 세트는 일반화 확인용으로만 쓰고, 릴리스 판정에는 새 봉인 세트를 쓴다(이번 릴리스만 봉인 생략, 사용자 결정 10-17).

## 3. 절차
1. **평가 — 릴리스 PR:** `Steve_ACASiaLAW` → `main` PR을 연다. 본문에 다음을 붙인다.
   - 성적표: 고정 시험·비공개 세트 건수(문장·이름 없음)·봉인 시험 점수
   - [일자별 추이표](DAILY_TREND.md)의 직전 릴리스 이후 행
   - 포함 라운드·해소 티켓·알려진 미해결
   - 버전 판정 결과(상향 또는 유지)
   - DB 마이그레이션 포함 여부
2. **CI:** 같은 SHA에서 `main` 필수 확인 3개가 성공해야 한다. 실패하면 병합하지 않고 원인을 티켓으로 남긴다.
3. **사용자 — 배포 전 확인:** 릴리스에 `migrations/` 변경이 있으면 병합 전에 Render 데이터베이스의 백업 상태를 확인한다. 이번 TK75 릴리스는 API·worker 모두 `LV_KOREAN_LAW_REVIEW_PROFILE=0` 또는 미설정 기본 OFF인지 확인한다. 기존 환경변수의 ON 값이 코드 기본값을 덮어쓰지 않도록 하며 키/환경변수 전체를 공개하지 않는다.
4. **사용자 — 병합:** 병합하면 Render가 자동 재배포한다.
5. **평가 — 태그(사용자 승인 범위 안에서):** **버전이 오른 릴리스에만** 병합 커밋에 `v.<버전>` 태그를 단다(예: `v.0.11.0`. 2026-10-09 사용자 결정으로 실제 관례 `v.0.10.0`·`v.0.11.0`에 맞춤). 버전을 유지한 릴리스에는 태그를 달지 않고, 판정서·HISTORY에 병합 SHA로 기록한다(2026-10-09 사용자 결정, 그전 `release-<YYYYMMDD>` 태그는 그대로 둔다). 태그는 지우거나 옮기지 않는다.
6. **배포 직후 온라인 점검(4절):** 사용자가 1회 실행하고 결과 JSON을 평가 측에 준다.
7. **평가 — 기록:** 판정서에 릴리스 기록(SHA·태그·CI·온라인 점검 점수)을 남기고, HISTORY에 측정값, DAILY_TREND에 그날 행을 남긴다.

### 4.2 사용자 실행 순서
1. 배포가 끝나면 `https://<서비스 주소>/api/health`를 연다. `commit`이 릴리스 PR의 병합 SHA와 같고 `database.status`가 `"ok"`인지 본다. 다르면 배포가 끝나지 않은 것이니 기다린다.
2. 새 프로젝트에 4.1의 PDF를 올린다.
3. 0.12.0의 2026-10-10 실행과 **같은 조건**으로 검증한다: 채점 규칙2판, 네트워크 사용, 실제 모델 ID/구성, 공식 DB 조회, 같은 Drive 참고자료 snapshot/선별 상태(육군 규정 포함). 이번 배포 정상 동작 점검은 TK75 **OFF**로 먼저 실행하며 품질 OFF/ON 비교는 별도 짝으로 기록한다.
   - 조건이 다르면(모델·채점 판·자료/선별 상태·Drive 폴더 등) 함께 알려 준다. 평가 측은 해당 항목을 '측정 못 함'으로 적고21/23과 증감 비교를 하지 않는다. 새 snapshot 비교는 같은 조건의 OFF/ON 쌍으로 따로 기록한다.
4. 결과 분석(보고서) JSON을 내려받아 평가 에이전트 세션에 올린다.

### 4.3 평가 측 처리
```
python scripts/score_report.py --report <보고서.json> --spec tests/fixtures/probes/case9_state_compensation_online.json --record --note "릴리스 <태그 또는 병합 SHA> 배포 직후 온라인 점검"
```
- 보고서 manifest의 `implementation.git_commit`(Render의 `RENDER_GIT_COMMIT`)이 릴리스 SHA와 같은지 확인한다. 다르면 측정하지 않고 사용자에게 알린다.
- 판정
  - 정상: 같은 조건·규칙2판에서21/23 이상이고, 0.12.0에서 통과한21항목 중 새 실패0. 총점만 같아도 이전 통과항목이 실패하면 정상으로 처리하지 않는다.
  - 회귀: 0.12.0에서 통과한 항목이 실패하면 티켓을 만들고 사용자에게 알린다. 기존 LEG-2/RAG-2 잔여와 새 실패를 구분한다. 되돌릴지는 사용자가 정한다.
- 되돌리기: `main`은 강제 푸시가 금지되므로 되돌림(revert) 커밋 PR로 되돌리거나, Render 대시보드에서 이전 배포로 돌린다.
