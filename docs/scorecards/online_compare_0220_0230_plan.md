# 0.22.0 → 다음 릴리스(예정 0.23.0) 배포 후 온라인 평가 계획

작성: 2026-11-18. 사용자 지시: 다음 릴리스 후 B 입력, case9 RAG, Drive 25자료, 공식 Source, 사용자 화면을 포함한 전 기능을 재측정하고, 평가 프로젝트를 정리한다. 이 문서는 **실행 계획**이며 다음 릴리스의 운영 통과·티켓 종결 판정이 아니다. 최종 버전명과 포함 PR은 릴리스 판정서에서 확정한다. 버전명이 0.23.0과 다르면 파일명을 그대로 두되 결과 보고서에 실제 버전·커밋을 명시한다.

기준 결과: [0.21→0.22 실측](online_compare_0210_0220_20261116.md), [TK-180 혼합 형식 추가 실측](online_0220_tk180_mixed_formats_20261116.md), [기능별 평가 규약](FEATURE_ONLINE_EVALUATION.md). 운영 0.22.0 기준 SHA는 `183f3d22791bb01d4c8a39ce842e193000c663b8`이다. 아래 수치는 이 배포의 관찰값이며, 다른 조건의 재실행과 직접 증감 비교하지 않는다.

## 1. 착수 조건과 실행 순서

1. **릴리스 확정:** 사용자 승인, 최종 후보의 필수 CI·통합 검증·적용되는 봉인 비교·버전 판정이 끝난 뒤 `Steve_ACASiaLAW` → `main` 릴리스 PR을 병합한다. 운영 Render의 배포 브랜치는 `main`으로 유지한다. 이 계획은 사전 게이트나 운영 승인 절차를 대신하지 않는다. #330 등 실제 포함 PR/TK와 기능 스위치 기본값을 최종 릴리스 SHA 기준으로 고정한다.
2. **운영 확인:** `https://verify-acas-law.onrender.com/api/health`에서 실제 버전, 전체 빌드 SHA, DB 상태를 확인하고 `main` 릴리스 SHA와 맞춘다. 캐시/이전 인스턴스가 섞이거나 실행 중 SHA가 바뀌면 수집을 멈추고 버전별로 분리한다. 태그·CI 성공만으로 배포 완료라고 판단하지 않는다.
3. **조건 기록:** 비공개 실행 장부에 실행 시각(한국시간), 계정 권한, 입력 A~D·case9 원본 및 B 원본의 SHA-256, 정답지/명세 판과 SHA-256, 채점기 판, 모델 ID·라우팅·출력 예산·프롬프트/정책, 공식 DB 공급자·기준일·가용성, Drive 폴더/25자료의 파일 ID·리비전·바이트 해시·색인 세대, RAG 스위치와 실행별 프로젝트/문서/실행 ID를 기록한다. 비밀값·세션 쿠키·원문 개인정보는 GitHub에 올리지 않는다. 정답지 기준 해시는 `84c059b851eb5b1a8c5c1cc2dc75668ede64a717b7002bb1c92af96327eb9e2c`이다. 달라졌으면 사유를 기록하고 양 버전을 같은 판으로 재채점한다.
4. **자료 준비:** 전용 평가 프로젝트를 생성하고 응답 ID를 즉시 [정리 장부 양식](online_project_cleanup_record.csv)에 기록한다. 기존 사용자 프로젝트는 사용·삭제하지 않는다. Drive의 검증된 공용 자료는 보존한다. 실험용 Drive 파일의 추가·교체는 파일별 리비전/해시와 색인 완료를 확인한 뒤 수행하며, 같은 이름의 TXT/PDF/DOCX/XLSX가 동시에 걸려 형식별 결과가 섞이지 않게 한다. case9 지지/무관 자료와 TK-180 형식 대조도 각각 구성·기록한다. 연결·색인·권한 준비가 안 된 항목은 `NOT_RUN`으로 둔다.
5. **실행:** 아래 순서로 **각 입력 하나당 보고서 하나**를 수집한다. (가) 운영 건강/권한/자료/인덱스 확인, (나) 원본 B와 A·C·D의 정답·구조·모델 경로, (다) case9 공식 DB·RAG 지지/무관 대조, (라) 동일 25자료 Drive 추출·검색, (마) 공식 Source 3공급자 cascade, (바) 입력 공격·TK-180 형식별 역할·개인정보 대조, (사) Time Table·참고자료 상세·내보내기·사용자 화면, (아) 포함된 신규 기능(#330 포함 시 NER·hybrid ON/OFF)과 회귀 대조. 최초 실패를 보존하고 재시도는 별도 회차로 기록한다.
6. **판정·보존·정리:** 원본 응답·보고서·실행 manifest·화면 증거와 채점 결과를 비공개 저장소에 보존하고 무결성을 확인한 뒤 평가 전용 프로젝트만 휴지통 이동한다. 결과와 정리 상태를 별도로 보고한다. 아래 중단 조건이 발생하면 신규 실행을 중지하고 이미 생긴 프로젝트의 증거 보존·안전한 정리는 계속한다.

## 4. 채점·보고 산출물

결과는 `docs/scorecards/online_compare_0220_0230_<실행일>.md`와 대응 JSON으로 남긴다. 항목별 **0.22 원본 근거 → 새 운영 원본 근거 → 조건 차이 → 분자/분모·미실행 → `RESOLVED`/`NOT_RESOLVED`/`REGRESSED`/`INCONCLUSIVE` → 원인·사용자 영향·해결/재시험 기준·담당 TK**를 기록한다. 해소는 실제 운영에서 원래 실패 경로와 음성 대조가 함께 통과할 때만 준다. CI·사본·직접 모델 호출·합성 보고서 성공은 별도 증거로만 적는다. 조건이 달라 전후 수치를 직접 비교할 수 없으면 차이를 설명하고 동일 판 후향 재채점 또는 대조 실험으로 확인한다.

보고서에는 릴리스/운영 전체 SHA, 배포 시각, 포함 PR·TK, 명세/입력/자료 해시, 모델·DB·RAG 상태, 최초 실행과 재시도, 화면 증거, 외부 장애, 비용·시간, 미측정 범위를 포함한다. 실패·미해소는 같은 원인 TK와 `NEXT_FOR_ANTIGRAVITY`에 재현 조건·수정 방향·수용 기준을 연결하고, `version_verdicts`·티켓 상태·`DAILY_TREND`를 실제 측정에 맞춰 갱신한다. 비공개 원문·인증정보·프로젝트 ID는 저장소에 싣지 않는다.

## 5. 평가 전용 프로젝트 정리

기본 절차는 [기존 정리 절차](online_compare_0210_0220_plan.md#4-평가-프로젝트-정리--모든-온라인-평가에-적용)와 [장부 양식](online_project_cleanup_record.csv)을 따른다. 이번 실행마다 다음을 확인한다.

1. 생성 응답의 정확한 프로젝트 ID, 평가 전용 여부, 문서/실행 ID를 비공개 장부에 즉시 기록한다. 빌린/기존 프로젝트와 공용 Drive 자료는 삭제 대상에서 제외한다.
2. 모든 실행이 완료·부분완료·실패·취소의 종료 상태인지 확인한다. 보고서·원본 응답·입력/명세·manifest·화면·오류·조건을 비공개 묶음에 보존하고 SHA-256과 재열기/압축 무결성을 확인한다. 보존 실패면 `CLEANUP_BLOCKED`로 둔다.
3. 삭제 직전 생성 장부의 ID·소유·문서/실행 목록을 API와 대조한다. 모르는 항목이 있으면 해당 프로젝트만 보류한다. `DELETE /api/projects/{project_id}`의 204를 받고 활성 목록에서 사라졌으며 삭제 목록에 같은 ID의 `deleted_at`이 생겼는지 확인한다. 409/통신 중단은 상태를 재조회하고 미확인을 성공으로 기록하지 않는다.
4. 삭제 결과 `TRASH_VERIFIED`/`CLEANUP_BLOCKED`와 근거 묶음 해시·보류 사유를 별도 보고한다. 기본 삭제는 휴지통 이동이며 `purge`는 호출하지 않는다. 다음 시험은 새 전용 프로젝트에서 시작한다.

실행 종료 기준은 **필수 항목별 판정 또는 명시적 미완료**, 원본 증거 보존, 평가 전용 프로젝트의 정리/보류 사유, 사용자에게 전달할 미해소·회귀 개선안까지 모두 기록한 때다.
